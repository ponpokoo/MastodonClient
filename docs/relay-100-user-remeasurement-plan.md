# 公開後100人を想定したRelay再測定計画

- 記録日：2026-10-07
- 状態：ハイブリッド方式を採用。今回のPush試験は2026-10-09で終了し、残る確認は[実運用へ引き継ぐ](../relay/workers/hybrid.md#採用後の対応と確認)。本計画は当初の測定条件・合格基準を保持し、利用規模の増加や問題発生時に必要な検証を選ぶ資料とする。全項目を消化する追加試験は予定しない。
- 2026-10-08の本番切替は旧APKの大通知欠落を許容する[ADR 0015](adr/0015-production-hybrid-cutover.md)による。[配置記録](investigations/relay-production-hybrid-cutover-20261008.md)を参照する。試験終了を100人・200購読の運用性能の合格とは扱わない。
- 実行記録：[100人・各1端末の再測定](investigations/relay-100-user-measurement-20261007.md)。
- 採用方式：[ハイブリッドRelay](../relay/workers/hybrid.md)、[ADR 0013](adr/0013-adopt-hybrid-push-delivery.md)。テスト・測定の入口は[検証ガイド](../relay/workers/testing.md)。
- 候補の実行記録：[ハイブリッド・100人条件の測定](investigations/relay-hybrid-100-user-measurement-20261007.md)。
- 前提：公開後の最大利用者数を100人と見込む。月額0円、開発者1人、Workers＋D1で検証する。

目的は、100人分の通知を無料枠で扱えるか、遅延・障害・登録濫用時に安全に停止・復旧できるかを判断すること。
100人は容量計画の見込みであり、一般公開で人数を強制制限できるという意味ではない。
全員がPushを使う条件で測定し、実際の利用が少なくても100人が集まるまで公開判断を待たない。
責任分担・秘密情報の境界は[本運用手順](relay-production.md)、[ADR 0009](adr/0009-relay-cloudflare-deployment.md)、
[ADR 0010](adr/0010-relay-subscription-key-binding.md)・[ADR 0013](adr/0013-adopt-hybrid-push-delivery.md)を維持する。通知到着・24時間対応の保証は設けない。

## 採用方式の再測定計画

以下は2026-10-07時点の測定案・判定目安を保持した参照資料。規模増加や問題発生時の再検証に必要な条件を選ぶために使い、現在の実運用での確認方針は[採用仕様](../relay/workers/hybrid.md#採用後の対応と確認)に従う。

100人×2アカウント×1端末、200購読、6,000通知/日、集中500通知/60秒を維持する。
小通知だけ・大通知だけ・1KiB 90%／4KiB 9%／64KiB 1%の模擬分布を分ける。模擬分布を実利用比率と扱わない。
旧方式の24時間本文保持・1,000件滞留の再送合格基準は、ハイブリッドへ適用しない。
新経路では本文保持0を確認し、欠落回復はAndroidの差分同期で判定する。

| 順序 | 対象と記録 | 完了の条件 |
| --- | --- | --- |
| A | 通常負荷の内部エラー1件の切り分け | SQL段階の匿名エラー分類・原因・対応を記録し、通常1,000件を再測定。意図した拒否と内部エラーを分ける |
| B | 本番相当のCPU・実FCM | 測定SQLの負荷を減らし、署名・初回OAuth・更新・送信・登録入替・拒否要求・日次清掃のCPUを経路別に確認。HTTP／FCM受付／端末表示を分ける |
| C | Android差分同期・集約・隔離 | account単位のUnique Work、複数Pushの集約、差分の全ページ取得後の位置更新、ID重複排除、失敗・切替・解除後の遅延応答を確認。APIはサーバー差も含めて公式仕様で確認 |
| D | 欠落・障害・端末負担 | 小通知のAPI不要表示、大通知同期、onDeletedMessages、起動・通知画面更新、通信切断後の回復を確認。API回数・通信量・電池・表示遅延を記録 |
| E | 24時間の資源・清掃 | 200購読・6,000通知/日を実時間で観測。日次Cronの実起動、本文0、カウンター清掃、登録入替・墓標・拒否要求・他DB分を含む日次費用を確認 |
| F | 監視・停止・復元・移行 | 通知到達、4停止スイッチ、再開後の解除隔離、Time Travel／隔離SQL復元、共有FCMトークンの2アカウント、対応APKの能力確認・旧fetch終了・差し戻しを記録 |

障害試験は、模擬FCM停止2時間に通常500件＋集中500件、復帰後250通知/時の条件を引き継ぐ。
Relay内に滞留を作る目的ではなく、失敗応答と、同期可能なMastodon通知をAndroidで補完する確認に使う。
通知APIから取得できない通知・期限切れ・削除・非対応サーバーは別に記録し、回復成功へ数えない。
実サーバーへ大量通知を投入せず、負荷部分は隔離した模擬環境、実機は少量の通知で確認する。

公開判断では従来の資源目安（他用途込み無料枠50%未満）、CPU超過0とp99 8ms以下の余裕目安、
正常時TTL 60秒以上の通知99%以上が60秒内にFCM受付する内部目標を引き継ぐ。
10msを超えるCPU観測と内部エラーは原因・公開可否を再評価する。短時間測定だけでは合格にしない。
Androidの欠落回復時間と許容遅延は実装・端末観測から確定し、旧Relayの60分滞留解消を代用しない。

段階観測は限定10人程度で7日、最大30人までで14日、一般公開後14日間は毎日を目安に維持する。
50%警戒・70%新規登録／拡大停止・80%受付制限、予算0円、解除情報不明時の墓標化・再登録方針も維持する。
実運用での確認事項は[採用仕様](../relay/workers/hybrid.md#採用後の対応と確認)、値・確認版は各[測定記録](../relay/workers/testing.md#調査とクラウド測定の順序)に残す。

## 旧保存方式の計画（比較・経緯の記録）

以下の1〜4はハイブリッド採用前の保存・fetch・永続再送方式を評価した計画。
旧方式が資源条件を満たさなかった根拠と、共通の監視・復元条件の参照用に保持する。
現在の配送・障害回復・実運用での確認方針は[採用仕様](../relay/workers/hybrid.md#採用後の対応と確認)を参照する。

### 1. 測定条件と規模

以下は再測定に使う暫定値。利用実績・変更済みの上限・合格実績ではない。

| 条件 | 100人向けの値と算定 |
| --- | --- |
| 有効購読 | 1人2アカウント×1端末、200購読。異なるサーバー鍵も含める |
| 通常流入 | 1購読30通知/日、6,000通知/日＝250通知/時＝約4.17通知/分 |
| 集中流入 | 通常流入に加え、約8.33要求/秒を60秒、計500通知。実測の件数・経過時間を記録 |
| 暗号文サイズ | 通常は1 KiB 90%、4 KiB 9%、64 KiB 1%。別に全fetch・4 KiB、最大64 KiBを測る |
| TTL | 保存試験は24時間。別に0・60秒・短いTTL・期限切れを測り、失効を配送成功に含めない |
| 障害 | 模擬FCMを実時間で2時間停止。通常500通知＋集中500通知、計1,000件の滞留を作る |
| 復旧中の流入 | 通常の約4.17通知/分を継続。分ごとの整数配分で1時間250通知を投入する |
| 保存 | 全fetch・24時間保持で通常6,000件＋集中500件。FCM受付済みの保存分も総件数に含める |
| 登録の入替 | 200有効購読に仮登録・無効登録・墓標を加え、再登録・トークン更新を測る |

通常6,000通知がすべてfetchなら、Push＋1回の取得で12,000 HTTP要求/日が目安。
これに登録・更新・解除・再取得・拒否要求・監視・他サービスの使用を加える。
D1のインデックス更新・Cron・期限切れ削除・測定用SQLも使用量に含め、通知数だけで無料と判断しない。
最大64 KiBを全fetchで6,000件保持するとBase64本文だけで約500 MiBになり、ヘッダー・索引等を加える前に単一Free DBの500 MB上限へ余裕がなくなる。
この条件は過負荷時の拒否・部分停止を確かめる試験とし、無制限に保存できる提供条件にはしない。
通常分布や4 KiB全fetchでも成立しない場合は、提供する流量・保持容量を見直して再測定する。

### 2. 再測定前に準備すること

現行の[src/store.mjs](../relay/workers/src/store.mjs)は登録120件（仮・無効を含む）、仮登録30件、
保持通知1,000件・登録別100件、Push日次20,000要求。Cronは毎分最大20件でDB文数でも打ち切る。
このままでは200有効購読と24時間のfetch保持を測定できず、1,000件滞留に新規流入・配送済みfetchの余裕もない。

1. **候補上限を別作業で実装する**：総登録300件（有効200＋仮50＋無効50の検証余地）、
   仮登録50件、総保持通知8,000件を出発案にする。墓標10,000件、登録別100件、
   Push日次20,000要求は先に引き上げず、入替・偏った流入・拒否要求を含めて評価する。
   8,000件は未送信と配送済みfetchを合わせた件数。保存バイト量による制御も比較し、実測で確定する。
2. **再送方式を再評価する**：1,000件を60分で解消するには滞留分だけで約16.7件/分が必要。
   新規流入も同じ再送経路で扱う場合は約20.8件/分以上が最低値となる。
   現行最大20件/分は初回送信で新規流入を処理できる場合でも余裕が少なく、DB文数で20件未満へ打ち切る点を実測する。
   件数の定数変更だけでなく、CPU・D1文数・リース・公平性を満たす方式を比較する。
   構成や共有境界を変更する判断は実装時にADRへ記録する。
3. **測定ツールを拡張する**：[bench](../relay/workers/bench/README.md)の固定120登録・90分期限・
   毎分3件の追加流入・固定originを、明示した条件へ変更できるようにする。
   2時間停止＋60分復旧用は準備時間を含む5時間、24時間保持試験用は26時間を期限の出発案とする。
   期限後の停止、誤環境への接続防止、Google通信の模擬化、ログの秘密値除外を保つ。
   受付・FCM受付・期限切れ・その他の破棄を突き合わせられる匿名集計を追加する。
4. **隔離環境を用意する**：新しい専用Worker・空の専用D1・模擬FCMを使う。
   本番DBと実FCMの資格情報は接続しない。Cronの反映・実起動を少量通知で確認してから負荷測定を始める。
5. **変更を確認する**：Workers実装・測定ツールを変更した場合は影響する確認と`relay/workers`の`npm test`を行う。
   Androidを変更した場合だけ[開発ガイド](project-setup.md#ビルドと確認)に沿う。

現行上限の境界確認と100人向け候補の測定は、配置版・設定・結果を分けて残す。
本番の上限引上げは、候補の測定と公開判断を終えてから行う。

### 3. 再測定の順序と合格基準

2026-10-07の初回測定は通常・集中・全fetchの資源評価で不合格となった。
日次書き込みの余裕不足と全fetchの読み取り超過見込みを[実行記録](investigations/relay-100-user-measurement-20261007.md)へ残した。
現候補の一般提供は見送り、資源条件を修正した最終構成で以下の長時間・運用確認を実施する。
資源条件の不合格を確認した時点では、B・Cを未検証として明記して公開不可を判断できる。
公開可を判断する場合はA〜Cの全確認を満たす。

#### A. CPU・DB・通常配送・保存

- 登録・鍵確定・鍵変更・トークン更新・解除・fetch、署名拒否、初回OAuth認証・更新を経路別に測る。
  同じ鍵・認証キャッシュの再利用時と、未キャッシュ時を分ける。
- 200購読で通常負荷・集中負荷・全fetchを測り、TTL削除を含む24時間の保存量を確認する。
  DB量は本文の計算だけでなくBase64・ヘッダー・インデックス・墓標を含める。
- 合格案：通常時、TTL 60秒以上の対象通知の99%以上が受付から60秒以内に模擬FCM受付へ到達。
  対象通知1,000件以上で評価し、端末表示とは区別する。破棄や再試行打切りを成功に数えない。
- CPUは経路別のp50・p95・p99・最大値と制限超過を記録する。
  Freeの制限超過0件、p99が8ms以下を余裕の目安とし、10msを超える観測があれば原因と公開可否を再評価する。
  本番相当版と測定ラッパーの差を確認し、通信待ち時間をCPUに置き換えない。
- 日次要求数・D1読み書き・保存量は、通常条件と全fetch条件のそれぞれで、他用途を含む見込みが無料枠の50%未満を合格案とする。
  平均値だけで合格にせず、ピーク、更新・解除・監視・復元用の余裕も確認する。

#### B. 再送・障害・容量

- 過去との比較用に600件の滞留を再測定した後、100人条件の2時間停止・1,000件滞留を測る。
  復旧後も1時間250件の通常流入を継続し、少数購読への集中と200購読への分散をそれぞれ確認する。
- 復旧開始は模擬FCMを成功へ切り替えた時刻。最初のCronまでの待ち・バックオフも60分に含める。
  手動Cron、保存済み再試行時刻の変更、測定中のCron設定修正は合格試験へ混ぜない。
- 合格案：60分以内に障害中の配送対象がFCM受付へ到達し、継続流入の未送信も平常水準へ戻る。
  単に未送信0件になっても、期限切れ・最大試行回数到達・永久エラーで消えた分は復旧成功にしない。
  復旧試験のTTLは終了まで十分に残す。短いTTLの欠落は別試験で確認する。
- 登録別待ち時間・送信数・リース競合を記録し、特定購読が残り続けないことを確認する。
  CPU・D1文数の上限内で再送が動き、既存の更新・解除・取得が継続できることを確認する。
- 保持上限・登録別上限・日次上限・最大本文時は、想定した拒否と停止が成立することを確認する。
  これらの過負荷試験での拒否は正常負荷の配送成功率と別集計する。

#### C. 監視・部分停止・復元・実機

- 50%警戒・70%新規登録／拡大停止・80%Push受付制限の指標、UTC集計期間、評価間隔、通知先を照合し、
  通知到達と担当者による停止操作を確認する。無料で通知できない指標は手動確認で補う。
- 通常時は未送信500件または最古15分で警戒、800件または30分で拡大停止する既存案を維持する。
  意図的な障害試験ではこの警戒を観測したうえで試験を継続する。容量が増えても警戒値を自動で引き上げない。
- 計画した過負荷以外でCPU制限超過、DB上限、想定外のGoogle通信、秘密値の記録、購読隔離の不備があれば測定を止める。
  使用量が70%へ到達する見込みなら新しい負荷試験を開始せず、80%で合成Pushを停止する。
- 新規登録停止・Push受付停止・送信停止・全体停止を個別に確認し、再開後も解除済み購読が復活しないことを確認する。
- [Workers復旧計画](../relay/workers/setup.md#バックアップと隔離復元)に沿い、
  Time Travelは模擬データの検証DB、SQL復元はFCMへ接続しない隔離DBで試す。
  バックアップ後の解除反映、解除履歴不明時の墓標化・端末再登録、退避の暗号化と期限内削除を確認する。
  内部目標RPO 24時間・復旧48時間を、手順と実測時間から評価する。
- 少量の実通知は異なる対応Mastodonサーバー2つ程度と物理端末で確認する。
  Release／Play配布候補でinline・fetch、背景・画面消灯・Doze・切断・再起動・切替・解除を確認し、
  Relay受付→FCM受付→受信・復号・表示を区別して記録する。
  全既存購読の移行結果と未移行端末の更新・起動案内も記録する。

### 4. 観測と一般公開の判断

1. 開発者の検証後、限定テストは従来の最大30人で進める。10人程度の段階で7日、30人までの段階で14日を観測目安にする。
   人数不足は200購読の合成測定で補い、Google Play側のテスト要件とは別に管理する。
2. A〜Cの合格記録、監視・停止・復元・移行案内と、200購読相当の容量候補が揃った時点で一般公開可否を判断する。
   実装上限だけを引き上げたり、100人という見込みだけで濫用対策が完了した扱いにしない。
3. 一般公開前に、一般利用者の登録を許容する範囲と濫用対策を記録する。
   資格確認を導入するか、容量・頻度制限と手動停止で受け入れるかを測定結果から判断する。
   人数の識別・強制制限がない場合は、100人を超える利用や拒否要求も止められる手順を必須にする。
4. 一般公開後14日間は毎日、安定後は週1回を目安に使用量・失敗・滞留・問い合わせを確認する。
   一般公開で10→30→100人を強制的に段階配信できるとは扱わず、閾値でRelayの新規登録／受付を停止する。
5. 100人条件で不合格なら原因を修正して該当部分を再測定する。0円で成立しなければ、Push提供範囲を縮小するか一般公開時の提供を延期する。
   有料移行は予算の変更を決めた場合の別判断とする。
