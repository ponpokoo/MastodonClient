## 1. この計画の進め方

既存機能を使える状態でGoogle Playへ公開し、開発者1人で継続できることを目指す。
初めは限定テスターで確認し、一般公開はアプリの品質と通知の運用範囲を確かめてから進める。
個人開発向けに、公開前の必須事項、公開する機能に応じた確認、後から改善できる事項を分ける。

本書は公開準備の計画であり、機能追加・料金・対象年齢・配信国を決定した記録ではない。
現行動作は[UI・機能仕様](ui-guidelines.md)、対象版と確認記録は[リリース計画](release-plan.md)、
Relayの運用条件は[本運用への移行手順](relay-production.md)を正本とする。
それらの採用済み方針や未完了の確認を、本書の簡略化によって変更・完了扱いにしない。

今回確認したのはコード、プロジェクト資料とGoogle公式の公開要件。
既存の動作・ビルド結果は資料から引用し、今回の文書改訂で再試験した結果とは区別する。
Play Console、公開ポリシーの外部URL、Firebase・Cloudflareの実設定は今回未確認。
Googleの要件は申請時にも公式資料とConsoleで確認する。

2026-10-07の追記：Issue #10・#11はGoogle Play公開に向けた品質・操作導線の整備として扱う。
設定からの登録削除確認と並び順の永続化を実装した。動作・検証範囲は[リリース計画](release-plan.md)と
[アカウント管理の仕様](ui-guidelines.md#登録済みアカウントの管理)を参照する。Googleの必須要件として追加したものではない。
アカウント管理・投稿のボタン順・投稿下部アイコンの並び替えは、右端のハンドルを使う共通のドラッグUIへ統一した。
この追記のコード検証は作業ツリーのDebug版を対象とし、上記コミットのRelease APK・AABやPlay配布版の再確認とは区別する。

| 領域 | 個人開発での進め方 |
| --- | --- |
| 公開資料 | 無料の静的Webページにプライバシー、利用規約、安全基準、削除案内をまとめる。見出しごとのURLで参照できる形を候補にする |
| 問い合わせ | サポート用メール1つを基本にし、不具合の公開管理にはGitHub Issuesを併用する。個人情報や安全に関する相談はメールで受ける |

Google Playの必須要件と、データ漏えい・誤投稿・保存済み内容の消失を防ぐ確認は残す。
専用の管理システム、有料監視、紹介動画、多言語展開、全端末・全サーバーの組み合わせ試験は初回公開の前提にしない。

## 3. 公開前に必要な最小セット

### 公開ページとアプリ内の入口

次の説明を短くても具体的に用意し、アプリ内から開けるようにする。
1つのサイトとサポートメールで管理できる構成にする。ポリシー本文はログイン不要のHTMLで公開する。
Googleは全アプリにプライバシーポリシーを求め、公開URLとアプリ内のリンクまたは本文が必要。
PDF・地域制限・閲覧者による編集は認められない。[プライバシーポリシー要件][g3]

| 説明 | 最低限含める内容 |
| --- | --- |
| プライバシー | Nagisaまたは開発者名、連絡先、利用するデータと目的、送信先、保存期間・削除方法 |
| 利用規約・投稿ルール | 禁止する投稿・行動、サーバーの規約も適用されること、報告・ブロックと開発者窓口、対応範囲 |
| 子どもの安全基準 | CSAE（子どもへの性的虐待・搾取）の禁止、報告経路、判明時の対応、関係法令に沿う対応、連絡先 |
| 削除案内 | 端末のログアウト、Relayの解除、Mastodonアカウント自体の削除を分けた説明 |

UGCを扱うクライアントにも、投稿・アップロード前の規約またはユーザーポリシーへの同意、
投稿・利用者の報告、ブロック、適切なモデレーションが必要。
既存の報告はログイン先サーバーへ送る。開発者が全サーバーの投稿を削除できるとは説明しない。
開発者への相談を確認し、必要に応じてサーバー管理者へ連絡するなど、実行できる対応を規約に書く。
CWやセンシティブ画像のタップ展開だけで要件を満たすとは判断しない。
偶発的な性的コンテンツを許容する場合は、初期フィルター、その完全解除に少なくとも2操作、
子どものアクセスを防ぐ年齢確認、正確なレーティング回答の条件を確認する。[UGCポリシー][g5]

ソーシャル／出会いカテゴリに適用される子どもの安全基準では、公開基準、アプリ内の報告経路、
判明時の対処、法令順守、Googleへの専任連絡先が必要。成人向けでも免除されない。
開発者本人を担当として登録し、同じメールで相談を受ける構成を候補にする。
専用チームの設置を本書の追加条件にはしない。[子どもの安全基準][g6]

### Data safetyと削除の説明

申告用に次の表を埋める。新しい監査システムは作らず、実装・SDKの説明・実設定を根拠にする。

| 経路 | 確認・記載すること |
| --- | --- |
| 端末内 | 暗号化した認証・Push情報、設定、下書き・添付、ホーム・通知DB。ログアウトやアンインストールで何を消すか |
| 選択したMastodonサーバー | OAuth、投稿・メディア、報告、Push購読。サーバー自身のポリシーと削除方法 |
| Relay／Cloudflare | FCMトークン、購読公開鍵、管理情報、通知暗号文、アクセス情報・ログ・バックアップの実際の保持 |
| Firebase／Google | FCM SDKと配送に伴う識別子・処理。提出構成の自動初期化・通信とSDKの申告資料 |

端末内のみの処理、収集、共有の例外をGoogleの定義に照らして判断する。
通知暗号文のE2E暗号化とFCMトークン等の管理情報を分け、「暗号化しているので全部収集なし」としない。
回答は実際の提出AABと運用に合わせる。[Data safetyの定義][g4]・[Firebaseのデータ処理][g13]

ログアウト時のPush解除が失敗すると、現行実装では解除専用の旧認証情報を暗号化して保持し、
次回起動・前景復帰等で再試行する。「ログアウトで直ちにすべて削除」とは書かない。
Relayは解除後の復活防止用記録（墓標）を無期限保持する。解除、期限切れ、バックアップを含め、
実際に残る情報とその理由を説明する。詳細は[購読管理](push-settings.md)と[Relay通信契約](relay-protocol.md)。

アプリがアカウント作成を提供・誘導する場合は、アプリ内とWebからの削除申請経路が必要。
外部の登録画面へ誘導する場合も含まれるため、認証中に登録へ進める経路を確認して適用を判断する。
ログイン専用という説明だけで適用外にしない。任意のMastodonアカウントをNagisaで直接削除する機能の新設は、
その判断前には必須作業にしない。[アカウント削除要件][g7]

## 4. Pushは限定テストと一般公開を分けて判断する

現在のRelay計画は、**限定テスト最大30人、公開後最大100人の見込み、月額0円、開発者1人の運用**。
2026-10-07に公開後100人・1人2アカウント／1端末の方針を採用した。
200購読・通常6,000通知/日の[再測定計画](relay-100-user-remeasurement-plan.md)に沿って一般公開可否を判断する。
旧文書の「鍵の購読紐付け未実装」「毎回1件しか再送しない」等は現行の不足ではない。
測定専用入口で200購読の候補を用意し、[初回の資源評価](investigations/relay-100-user-measurement-20261007.md)を実施した。
日次書き込みの余裕不足と全fetchの読み取り超過見込みから、現候補は100人向け公開条件未達。
これは旧保存方式の評価。後続の[ハイブリッド測定](investigations/relay-hybrid-100-user-measurement-20261007.md)を経て、
[ハイブリッド配送を採用](adr/0013-adopt-hybrid-push-delivery.md)した。
Android同期の実装は完了。実FCMの回復・端末負担、内部エラー・CPU・長時間運用と購読移行は未完了。
本番設定は未変更で、一般公開でのPush提供可否は未判定。
現在の確認事項は[採用仕様](../relay/workers/hybrid.md#採用後の対応と確認)、検証記録の入口は[テスト・測定一覧](../relay/workers/testing.md)。

合成通知1,000件を受け付け、滞留600件が解消した記録がある。Cron設定変更・待機・手動確認を含み、
60分以内の復旧目標やFreeのCPU余裕の合格記録にはなっていない。
既存の方針では再送性能の再測定を限定テスター確認の開始条件にせず、実配送確認へ進める。
残る確認は[測定記録](investigations/relay-production-measurement-20261006.md)と[Issue #8](https://github.com/ponpokoo/MastodonClient/issues/8)で管理する。

| 公開段階 | 判断と作業 |
| --- | --- |
| 最大30人の限定テスト | 現行計画で進める。既存購読の移行、別サーバーでの実通知、物理端末の画面消灯・再起動・解除を確認する。使用量・失敗・滞留を見て募集を止められるようにする |
| 一般公開でもPushを提供 | 採用したハイブリッド方式で100人・200購読の無料枠、Android差分同期・欠落回復、24時間運用・日次清掃、監視通知、停止・隔離復元、実機・購読移行を確認する。100人は強制制限ではなく、登録濫用・見込み超過時の対応も記録する |
| 初回の一般公開でPushを提供しない | 一般公開用の構成では有効化できないようにする。既存購読の停止・解除・移行案内を決め、起動中／定期確認のAndroid通知を確認する。設定とストア説明も合わせる |

一般公開の予定をPushの拡張完了だけに依存させず、提供しない構成も選択肢にする。
どちらを採用するかは公開前に決める。構成変更が必要なら実装と確認を別作業で行う。
Firebase Messagingは現行の依存関係に含まれるため、Relay URLを空にするだけでSDKの通信や申告が不要になるとは判断しない。

監視はCloudflare／Play Consoleの既存画面と利用可能な無料アラートを使う。
通知内容・トークン・配送URLをログへ出さず、使用量、エラー、未送信件数を確認する。
一般公開前の具体的な条件は[Relay運用手順](relay-production.md)・[Workers配置・復旧計画](../relay/workers/setup.md)に従う。
本書で稼働率や配送時間の保証を追加しない。

## 5. 公開までの手順

### 手順1：Consoleの準備とテスター募集を始める

アカウント種別・作成日、本人確認、必要な端末確認、公開される開発者情報をConsoleで確認する。
初回登録料は25米ドルの一回払い。Relayの月額0円とは別の費用として扱う。[Console登録][g8]

2023-11-13以降に作成した個人アカウントには、12人以上が14日間以上連続でオプトインした
クローズドテストが必要。該当する場合は募集を早めに始め、退出を考慮して15人程度を募集目安にする。
15人は本書の推奨でありGoogleの追加要件ではない。GitHub配布・内部テストでは期間を代替できない。
試用内容とフィードバックも残す。[個人アカウントのテスト要件][g1]

この段階で、初回の機能範囲、無料／有料、広告・課金、配信国、対象年齢、一般公開時のPush方針を決める。
無料・広告なし・スマートフォン中心は出発案。決定済みとして申告しない。

### 手順2：公開ページと必要な導線を用意する

第3節のページ、サポートメール、投稿前の規約同意、設定からの入口を整える。
Data safety等の回答を作り、削除要件の適用とコンテンツ表示・年齢確認を判断する。
依存ライブラリと使用素材のライセンスを確認し、必要な表示・NOTICEを用意する。

まずこれらの不足をIssues等の短い作業一覧にする。詳細な報告UIや全画面の説明書を同時に作る必要はない。

アカウント管理の公開前整備として[Issue #10](https://github.com/ponpokoo/MastodonClient/issues/10)の削除確認と、
[Issue #11](https://github.com/ponpokoo/MastodonClient/issues/11)の保存される並び順を含める。
削除の説明ではNagisaの端末内登録削除、Push・Relay解除、Mastodon上のアカウント削除を区別する。

### 手順3：署名と候補AABを固定する

既存GitHub版から上書き更新したい場合は、Playから届くAPKのアプリ署名鍵との互換性を先に確認する。
Play App Signingのアプリ署名鍵と、AABへ署名するアップロード鍵は役割が異なる。
既存鍵を引き継ぐ場合はConsoleの手順で登録し、別のアップロード鍵を使う構成を検討する。
異なる署名で更新できない場合は、下書き保存・再ログイン等の移行案内を用意する。[Play App Signing][g9]

2.4.1の既存AABは準備の出発点。公開導線・不具合・署名構成を変更したら、新しい候補として版番号・記録を更新する。
Consoleで使用済みのversionCodeを再利用しない。公開済みタグや配布APKを差し替えない。
コードを変更した最終候補では、[開発ガイド](project-setup.md#ビルドと確認)に沿って次を実施する。

```sh
./gradlew :app:testDebugUnitTest :app:lintRelease :app:assembleRelease :app:bundleRelease
```

Windowsでは`./gradlew`を`.\gradlew.bat`に置き換える。
AABの出力先は`app/build/outputs/bundle/release/app-release.aab`。
署名設定がなければ、タスク成功だけで署名済みとは判断しない。
コミット、版番号、AABのSHA-256、署名証明書、Firebase・Relayの構成を記録する。秘密値は記録・公開しない。

2026-10-06に参照したスマートフォン向け提出要件はtarget API 36以上。
現行の37は数値上満たすが、提出AABとConsoleで確認する。[対象APIレベル][g2]
依存SDKを含むネイティブライブラリの有無と、必要な16KBページサイズ対応も確認する。[16KB対応][g12]

### 手順4：Play配布版の主要操作を確認する

内部テストへAABをアップロードし、Playから入れたRelease版で下表を確認する。
手元の実機1台で主な経路を一巡し、最低対応Android 8と不足する通知権限環境などをエミュレーターで補う。
利用可能なテスター端末も使う。全OS・メーカー・テーマの掛け合わせを実施する必要はない。
異なるMastodonサーバーを2つ程度選び、対応する固有機能だけ追加確認する。

| 確認 | 最小限の操作・合格条件 |
| --- | --- |
| 認証・アカウント | 新規ログイン、取消、再起動、A→B→A、通信中の切替。Issue #10の削除対象・キャンセル・確認中の切替・削除後の遷移、Issue #11の並び替え・再起動・切替と投稿元の順序・追加／再認証／削除後の順序を確認する。別アカウントの表示・送信が混ざらない |
| 投稿・下書き | 公開範囲・返信・CW、保存→再起動→復元、通信失敗→再試行、連打。入力消失・二重投稿・意図しない投稿がない |
| 送信失敗後の別下書き | 失敗→別の下書き復元→送信。Issue #6の古い送信キー再利用が候補版に残っていないかを確認する |
| 共有・メディア | 画像・動画・音声、複数共有、未ログインからの共有、読めない添付。失敗を表示し、意図しない送信がない |
| 閲覧・通知欄 | 更新・追加取得、3種類の通知、非対応リアクション、ワードミュート、検索詳細から戻る操作が成立する |
| 安全操作 | 投稿・プロフィールの報告、ブロックと解除、CW・センシティブの初期表示。公開方針どおり動く |
| OS通知 | 許可拒否、背景・画面消灯・再起動、別アカウントの通知タップ。提供する経路が動き、混線しない |
| 更新・保存 | 既存Releaseから更新できるか、Room移行、保存済み下書き、ログアウト後の削除。再インストール／端末移行の保持・削除・再認証案内と一致する |
| 表示・安定性 | 文字拡大・明暗テーマ、一定時間の閲覧と再生。主要ボタンが使え、起動不能・継続クラッシュがない |

鍵・DBはバックアップ除外設定がある。下書き・添付・通常設定まで全て除外されるとは扱わず、
復元確認が必要な保持対象を設定と照合する。OS・外部入力・16KB等への変更がある場合は、該当する確認を追加する。
リリース前レポートの重大な指摘も確認する。

[Issue #5](https://github.com/ponpokoo/MastodonClient/issues/5)の下書き配送遅延は原因未確定。
通常投稿と下書き投稿のHTTP本文一致は確認されているが、サーバー側の配送や受信側の更新区間は未測定。
遅延だけを下書き不具合と断定しない。一方、[Issue #6](https://github.com/ponpokoo/MastodonClient/issues/6)の送信キー再利用は別の再現事象。
候補版で誤った送信結果の再利用や内容消失が残る場合は、公開前に直す。

記録は「候補コミット・版番号・AABハッシュ・構成・日時・端末/OS・サーバー・結果・残るIssue」で十分。
未実施は未実施と書き、パスワード・トークン・他人の投稿を記録へ入れない。

### 手順5：掲載情報を揃え、クローズドテストを行う

ストア素材は、名称30文字以内、短い説明80文字以内、詳細説明4000文字以内、
512×512のアイコン、1024×500のフィーチャーグラフィック、スクリーンショット最低2枚を用意する。
初回は主要画面4枚程度を目安にし、紹介動画は用意しなくてよい。
形式・容量は[ストア掲載設定][g10]と[画像の要件][g11]で確認する。

Mastodonアカウントが必要なこと、対応範囲、通知の条件、公式Mastodonアプリではないことを書く。
許可のあるテスト投稿を素材にし、Data safety、広告、対象年齢、レーティング、アプリへのアクセス、安全基準等をConsoleで回答する。
審査用に安定した専用アカウント、サーバードメイン、認証・主要操作の説明を登録する。認証情報は公開文書へ入れない。

クローズドテストでは参加URLと操作例を配り、実際に閲覧・投稿・通知等を使ってもらう。
フィードバックはメール、Playの非公開フィードバック、Issuesで集める。
適用される人数・期間要件と利用実績を確認し、改善内容を短く記録して製品版アクセスを申請する。
14日経過だけで公開が確定するわけではない。募集・各審査・修正の時間を見込み、公開日を先に固定しない。[テストとアクセス申請][g1]

### 手順6：一般公開の審査へ進め、公開後に確認する

一般公開用のPush方針と運用条件を満たし、テスト済みAAB、掲載情報、申告、公開ページ、審査用アクセスを最終照合する。
製品版アクセス承認後、製品版リリースを審査へ送信する。承認・配信開始後に一般利用者向けストアURLからインストールを確認する。
初回公開には割合指定の段階的公開を使えない。配信国を絞っても30人の人数制限にはならない。[段階的公開の適用範囲][g14]

公開直後はPlay Console、問い合わせ、Pushを提供する場合のRelay使用量・エラー・滞留を、対応できる日に確認する。
安定後は週1回程度を出発点にし、アラートや不具合報告があるときは追加確認する。頻度は本書の運用案。
データ漏えい・誤投稿等の重大問題は、可能な配布停止・Relay受付停止・利用者への案内を行い、版番号を上げて修正版を出す。
Relayの停止・復旧は既存手順を使い、公開済みの同じ版を差し替えて対応しない。

## 6. 公開判断のチェックリスト

- [ ] Consoleの確認と、適用されるテスト・製品版アクセス要件を満たした
- [ ] 公開ページ・問い合わせ先・アプリ内の入口・必要な同意を用意した
- [ ] 報告・ブロック、コンテンツ表示、年齢・安全基準、削除要件への対応を確認した
- [ ] Data safety等の申告が提出AAB・SDK・運用と一致した
- [ ] 署名・版番号・AABハッシュを記録し、既存版からの更新または移行方法を確認した
- [ ] Play配布版の主要操作が成立し、漏えい・誤投稿・保存済み内容の消失・主要操作不能が残っていない
- [ ] 一般公開時のPush提供範囲を決め、その構成と運用の未完了事項を解消した
- [ ] ストア素材と審査用アクセスを揃え、公開後の問い合わせ・停止・修正版配布の手順を確認した

操作不能につながらない見た目、画像遷移の演出、報告UIの細分化、探索の再設計、
ローカル・連合のDB化、多言語・タブレット専用対応等は後から改善できる。
個人開発でも、上の必須項目が未完了なら一般公開を待つ。実施した確認と既知の制約を説明できれば、
全ての改善候補が完了するまで公開を待つ必要はない。
