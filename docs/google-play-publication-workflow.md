# Nagisa Google Play提出・公開・更新のワークフロー

改訂日：2026-10-22

Nagisaは個人開発のAndroid向けMastodonクライアントで、現在クローズドテストを実施している。開発者からの2026-10-22の申告では、これまで深刻な問題は出ていない。この運用実績を踏まえ、通常の更新は変更箇所の確認を中心に進める。

今回の対象バージョンと変更内容は[リリース計画](release-plan.md#現行のリリース対象版)、成果物・確認結果・配布状況は版ごとの[内部リリースノート](release-plan.md#内部リリースノートの保管)で管理する。特定バージョンの提出・審査・配信状態はPlay Consoleで確認する。

## クローズドテスト中の更新

普段の提出は次の手順で行う。正式公開後の通常更新にも同じ手順を使う。

1. 前回の配布版との差分をまとめ、versionName・未使用のversionCodeを設定する。利用者向けの変更点と、今回確認する操作を短く決める。
2. [開発ガイド](project-setup.md#変更範囲に応じた確認)に沿ってテストとReleaseビルドを行い、AABの版番号・署名・SHA-256と対応コミットを記録する。同じコード・構成で成功済みの確認は再利用する。文書だけの変更では再ビルドしない。
3. 手元の端末1台を基本に、Release版の起動と変更箇所の代表的な操作を確認する。OS固有の処理や実機で確認しにくい条件に変更があるときは、該当する端末テストやエミュレーターで補う。
4. クローズドテストのリリースへAABと変更内容を登録する。対象トラック・バージョンを照合し、Consoleのエラーや対応が必要な項目を確認して審査へ送る。掲載情報や申告は、今回の変更やGoogleからの要請で更新が必要な部分を直す。
5. 配信されたら、Playから既存インストールを更新し、起動・変更箇所・普段使う画面を短く確認する。提出・配信の状態と結果を同じ内部ノートへ追記し、成果物と一緒にバックアップする。

毎回すべての機能、OS、サーバー、テーマを組み合わせて試す必要はない。通常の操作確認で問題がなく、変更箇所のテストが通っていれば、軽微な表示調整や改善候補はIssueへ残して更新を進める。既存の確認結果は確認したバージョンが分かる形で参照し、今回実施した確認と区別する。

## 追加確認を行う変更

次の変更があるときに、関係する確認だけを追加する。機能ごとの操作は[UI仕様](ui-guidelines.md)、テストの選び方は[開発ガイド](project-setup.md#ビルドと確認)を使う。

| 変更箇所 | 追加する確認 |
| --- | --- |
| 認証・アカウント切替・非同期処理 | ログイン・再起動・切替と、処理中の切替後に別アカウントの表示や送信が混ざらないこと |
| 投稿・下書き・添付 | 変更した送信／保存経路と、失敗・再試行時の入力保持や二重投稿の防止 |
| DB・設定・保存／削除・署名構成 | 既存版からの更新、対象データの保持・移行・削除。署名変更時はPlay配布版との更新互換性 |
| 通知・Push・権限・OS連携 | 変更した受信／通知タップ／権限の経路。必要な場合に画面消灯・背景動作を補う |
| API互換性・サーバー固有機能 | 影響するサーバーと、未対応時・取得失敗時の動作 |
| SDK・送信先・データ用途・公開範囲 | 関係するData safety、プライバシーポリシー、権限、対象年齢・レーティング等の申告と掲載内容 |

公開ページ・問い合わせ先・報告／ブロック・必要な同意・削除案内などは既存の導線を維持し、動作や申告に関係する変更があったときに照合する。Googleの要件への対応が未完了、または申告との不一致が分かっている場合は、その項目を個別に解消する。クローズドテスト中という理由だけで対応済みとは扱わない。[審査用の情報と申告](https://support.google.com/googleplay/android-developer/answer/9859455?hl=ja)

データの扱いは[保存・セッション管理](project-setup.md#通信認証保存の境界)、[Push購読管理](push-settings.md)、[Relay通信契約](relay-protocol.md)を参照する。ログアウト、Push解除、Mastodonアカウント自体の削除は区別し、解除待ち情報など実際に残るデータも説明に反映する。詳細を提出のたびに調べ直す必要はない。

## 正式公開へ進むとき

クローズドテストで得た利用実績とフィードバックを使い、次を一度確認する。テスター募集や初期設定を最初からやり直す手順には戻らない。

- Consoleに表示される製品版アクセスの条件と、必要な申告・審査用アクセスが揃っている。2023-11-13以降に作成した個人アカウントに適用される現行条件は、12人以上が14日間連続でオプトインしたクローズドテストで、条件を満たした後に製品版アクセスを申請する。[Googleのテスト要件](https://support.google.com/googleplay/android-developer/answer/14151465?hl=ja)
- 現在の候補で、起動不能・繰り返すクラッシュ・誤投稿・アカウント混線・データ消失など、利用に深刻な影響を与える問題が把握されていない。既知の軽微な問題や将来の改善はIssueで継続する。
- ストア説明、公開ポリシー、問い合わせ先、提供機能・Pushの範囲が実際の配布構成と合っている。

製品版アクセスの承認後、確認済みのAABを使って製品版リリースを審査へ送る。クローズドテストと同じAAB・構成なら、その確認結果を引き継ぐ。公開のためにコードや構成を変えた場合は変更範囲を確認する。

配信開始後はPlayからのインストールまたは更新と、起動・普段の閲覧・今回の変更箇所を確認する。提出、審査承認、配信開始は内部ノートで区別する。初回公開では割合指定の段階的公開を利用できない。[段階的公開の対象](https://support.google.com/googleplay/android-developer/answer/6346149?hl=ja)

## Push・Relayの運用

本番Relayはハイブリッド配送を採用済み。専用のPush試験は終了しており、残る通知到達・欠落回復・端末負担・使用量の確認は[既存の運用方針](../relay/workers/hybrid.md#採用後の対応と確認)に沿って進める。

通常のPlay提出や正式公開のために、一律の負荷試験・長時間試験を追加しない。公開時は現行のPush提供範囲と利用規模の見込みを整理し、問い合わせやRelayの使用量・失敗に変化があった場合に必要な確認を選ぶ。既存の[100人向け再測定計画](relay-100-user-remeasurement-plan.md)はそのための参照資料とする。試験未実施の規模について性能を保証しない。

Relayの停止・復旧は[Workers運用手順](../relay/workers/setup.md)に従う。個人で対応できる範囲を基本とし、常時監視や通知到達時間の保証は設けない。トークン、秘密鍵、通知本文、配送URLを記録へ出さない。

## 正式公開後の更新と不具合対応

普段の更新は「クローズドテスト中の更新」の手順を使い、提出先を製品版トラックにする。影響の大きい変更は先にクローズドテストへ配布し、必要に応じて製品版の段階的公開を使う。小さな修正ごとに新たなテスト期間や全機能の確認を設けない。更新の段階的公開は利用可能で、公開割合は手動で変更する。[段階的公開の操作](https://support.google.com/googleplay/android-developer/answer/6346149?hl=ja)

更新直後は、対応できる時間にPlay Consoleのクラッシュ・ANR、テスターや利用者の報告、Pushを提供する場合のRelay使用量・エラーを確認する。安定後も問い合わせやConsoleの通知をきっかけに必要な確認を行う。専用の監視システムや定例報告書は作らない。

重大な問題が出た場合は影響範囲を調べ、必要に応じて段階的公開や新規配信を止める。Relayが原因なら既存の受付停止・復旧手順を使い、利用者へ必要な案内を出す。修正版はversionCodeを上げて配布する。段階的公開の停止だけでは、更新済み端末が元のバージョンに戻ることはない。[公開の停止と再開](https://support.google.com/googleplay/android-developer/answer/6346149?hl=ja)

確認結果・提出・公開状況は内部ノート1つへ記録し、継続対応はIssuesに残す。公開されたことだけを理由に仕様書や計画書へ履歴を追記せず、動作・手順・提供範囲が変わった文書だけを更新する。
