# 0.2.0 リアルタイム通知の実装計画

本書は0.2.0の設計・進捗を記録する。Firebaseプロジェクトを作成してAndroidへ接続済み。
試験環境はWorkers Free＋D1、月額予算0円を目標に選定した。
公開Relayへの登録・解除と、利用者による実通知の到着確認まで完了。実機での継続試験へ進む。
現在の実装仕様は [UI・機能仕様](ui-guidelines.md)、検証方針は [開発ガイド](project-setup.md) を参照する。

## 目標と既存実装

前景ではMastodon Streaming API、背景ではMastodon Web Push → Nagisa Relay → FCM → Nagisaで通知する。
既存のStreaming受信、Android通知、簡易通知の配信履歴を利用する。
Push購読は前景でも維持し、前景・背景の境界で両経路から届いても二重表示しない。
FCMを含め、到着時刻や全通知の配信を保証するものではない。

## ローカル実装の進捗（2026-09-21）

段階ごとの記録。最新のRelay実装は[Workers試験版](../relay/workers/README.md)、
公開準備は[Web画面での設定手順](relay-workers-setup.md)を参照する。

- Workers Free＋D1へ登録・暗号文保存・VAPID検証・FCM HTTP v1送信・Cron再送を実装。
  ローカル23件のテストと配布用バンドル生成成功。公開環境のCPU 10msと実配信は未検証。
  Queuesは使わず、Cron再送は毎分最大1件。少数アカウントでの試験向け。

- Mastodon購読の取得・登録・解除をdomain Repositoryとdata実装に追加。
  IDは数値表現の応答も桁を維持してStringに変換し、未知フィールドを許容する。
- Relay専用の登録・FCMトークン更新・解除クライアントを追加。
  [登録API契約](relay-protocol.md)とMockWebServerテストを用意した。
- 新規通信テスト10件とDebugビルド成功。外部サービスへの接続は行っていない。
- P-256鍵、16 byteのauth secret、独立した32 byteのRelay登録ID・管理用秘密値の生成を追加。
  公開鍵は非圧縮SEC1、秘密鍵はPKCS8、各値はパディングなしBase64URLで保持する。
- `secure_push` DataStoreに購読ごとの秘密情報と進捗を暗号化保存する。
  本番は既存のAndroid Keystore AES-GCMを使用し、バックアップ・端末移行から保存ファイルを除外する。
  復号失敗は「購読なし」に置き換えず、エラーとして伝える。
- `DefaultPushRegistrationRepository`で登録中・有効・解除中を保存し、再呼び出しで再開する。
  Relay応答消失後は同じID・鍵を使用し、Mastodon登録応答消失後はGETで照合する。
  別のendpointへの上書き・削除を拒否し、認証情報やRelayの変更時にも秘密情報を再送しない。
- 解除は解除中状態を先に保存してRelayから停止する。失敗中は再有効化を拒否する。
  全解除成功後に保存情報を削除し、再有効化では新しい鍵・IDを生成する。
- 今回の追加テスト13件、前段の通信テスト10件を含む関連23件成功。
  その後、単体テスト全体102件成功（失敗・エラー・スキップなし）、Debugビルド成功。
- 画面・DIへの接続、OAuth権限追加、起動時の自動再開・再試行スケジューラー、
  ログアウト・再認証との接続、Relayサーバー、FCM受信・復号は未実装。
  再開には呼び出し側が同じセッションと希望する通知設定・最新FCMトークンを渡す必要がある。
  現段階では利用者向けの通知動作は変わらない。
- JVMテストの保存暗号には差し替え可能なJCA AES-GCMを使用した。
  Android Keystore、端末でのプロセス終了・再起動、バックアップ除外の実動作は未検証。

### 構成要素

| 構成要素 | 責務・保管情報 |
| --- | --- |
| Nagisa | インスタンスへの購読登録・解除、Web Push鍵生成と復号、FCM受信、通知表示 |
| Relay | 推測困難な配送先IDとFCMトークンの対応、暗号化ペイロードの転送、再試行と期限管理 |
| Mastodon | アクセストークンに対応するWeb Push購読と通知送信 |

Mastodonアクセストークン、Web Push秘密鍵・auth secretをRelayに渡さない設計を基本とする。
端末側の秘密情報は既存の暗号化保存方針に従う。FCMサーバー認証情報はRelayの実行環境だけに置く。
Relayには通知本文を復号する機能を持たせず、ログにも本文・トークン・配送先の秘密情報を記録しない。

## 実装順序

1. AndroidとRelayの通信契約、登録状態、失敗時の扱いを確定する。
   ローカルの模擬RelayとFCM代替実装で、外部サービスなしに検証できる境界を作る。
2. Androidに購読管理のドメイン契約とdata実装を追加する。
   UI → ViewModel → ドメイン → dataの境界を維持する。
   OAuthにpushスコープを追加し、既存アカウントには有効化時の再認証導線を用意する。
3. Relayの登録・宛先更新・解除・Web Push受信・FCM送信を実装する。
   配送先IDと管理用資格情報を分離し、宛先更新・解除に認証を要求する。
   リクエストサイズ制限、登録の濫用対策、期限付き再試行、無効なFCM宛先の削除を実装する。
4. AndroidにFCM受信、Web Push復号、共通通知処理への接続を追加する。
   Web Push本文はREST通知DTOと同一と仮定せず、専用DTOからドメインへ変換する。
5. FirebaseとHTTPSで到達可能なRelayを用意して実接続する。
6. 通知設定と購読状態を表示し、複数アカウント・実機で検証する。

## 外部サービスの準備

ローカルの設計・単体テストには外部アカウントを必要としない。実配信の前に次を準備する。

- FirebaseプロジェクトとAndroidアプリ登録。application IDは既存の
  `io.github.ponpokoo.mastodonclient`を使用する。
- Android用Firebase設定と、RelayからFCMを送信するためのサーバー側認証設定。
  サーバー認証情報をAPKやGitへ含めない。
- 公開HTTPSエンドポイントを持つRelayの実行環境と、配送先・再試行を保存する永続ストレージ。
- 通知を発生させられるテスト用MastodonアカウントとFCMを利用できるAndroid端末。

試験版はCloudflare Workers Free＋D1、JavaScript、月額予算0円を目標とする。
無料枠内での利用量とCPU時間は公開環境で確認する。独自ドメインは必要条件にしない。
サービスの契約、課金の有効化、公開デプロイはこの設計文書の作成には含まない。

## 実装前に詰める互換性と配信条件

- Mastodonの購読はアクセストークンごとに1件で、再登録は既存購読を置き換える。
  再試行時にはサーバーと端末の状態を照合する。
- 標準Web Pushと旧形式、サーバーバージョンごとの対応フィールドを確認し、
  全インスタンスが同一仕様と仮定しない。暗号実装には仕様・既知ベクトルによる検証を行う。
- 暗号化本文をBase64化した後のFCMサイズ制限を確認する。
  超過時に切り捨てて転送せず、期限付き暗号文の取得方式などを通信契約で決定する。
- FCMはdataメッセージによる共通通知処理を基本案とする。
  表示対象の通知を高優先度で送り、受信処理中の長いネットワーク処理を避ける。
- アカウントごとに購読し、閲覧中でないアカウントも配送対象にできるようにする。
  重複判定はセッションと文字列の通知IDで分離する。
- FCMトークン更新は全対象購読へ反映する。ログアウト・通知無効化では購読とRelay宛先を解除する。
  オフライン解除の再試行と、解除後に遅延通知が届いた場合の抑止を設計する。
- Push未設定・非対応時は既存の簡易通知を利用できるようにする。
  Push有効時の定期確認と、前景通知設定との関係は設定仕様として明文化する。

## 完了条件

- 登録途中の失敗から復帰し、購読・暗号鍵・宛先の不整合を修復できる。
- 同一通知のStreaming／FCM／簡易通知による同時受信で二重表示しない。
- アカウント切替・ログアウト・再認証・FCMトークン更新後に宛先が混ざらない。
- 不正暗号文、未知の通知種類、期限切れ、サイズ超過を安全に処理する。
- Relayの再送、FCM一時エラー、無効宛先を検証する。
- 前景、背景、通常のプロセス終了、Doze、通知許可拒否、強制停止を区別して実機確認する。
  未確認の条件を到達保証として記載しない。
- 影響する単体テストとビルドを実施し、配布候補では開発ガイドのリリース確認を行う。
