# 保守・機能追加・リリース計画

クローズドテストは終了し、製品版を公開済み（2026-11-06の利用者確認）。今後は保守と機能追加を中心に、採用済みの更新範囲とリリース手順を管理する。過去版の更新内容・成果物・確認結果・配布状況は、Git管理外の版ごとの内部リリースノートに保管する。
現行動作は[UI・機能仕様](ui-guidelines.md)、確認方法は[開発ガイド](project-setup.md#ビルドと確認)を参照する。過去の検証結果を今回の配布候補の結果として扱わない。

## 開発の優先順位

1. クラッシュ、誤投稿、アカウント混線、データ消失など、利用への影響が大きい不具合を優先して修正する。
2. OS・サーバー・依存ライブラリとの互換性、通知・Relay、既存機能の使い勝手を保守する。
3. 機能追加はIssueで目的・対象範囲・未対応サーバーでの動作を決め、採用する更新に含める。

継続作業と進捗はIssuesで管理し、仕様や運用が変わった文書だけを更新する。初回公開の準備や製品版アクセス申請を通常作業に含めない。

## 現行のリリース対象版

以下は配布候補の計画であり、製品版として公開済みの版番号を示すものではない。公開版と配布範囲は内部リリースノートで確認する。

リリース準備対象はversionName `3.0.4`、versionCode `36`とする。`app/build.gradle.kts`も同じ版番号に揃え、Google Play提出用の署名付きAABを準備する。確認用APKは必要な場合に同じソースから生成する。成果物・検証結果・提出と配布の状況は版ごとの内部リリースノートに記録する。

比較元は3.0.3の提出用AABに対応するソース `2829a5efefa14367b599d185952c5fdd01bb04d9`。前回の記録は`app/release/Nagisa-3.0.3-vc35-release-notes.md`、今回の記録先は`app/release/Nagisa-3.0.4-vc36-release-notes.md`とする。3.0.3の配信状況は未確認。

現在の表示・操作は[UI・機能仕様](ui-guidelines.md)に従う。

### 3.0.4の配布前に確認すること

- 既存版からの更新後にログイン状態と設定が保持されること、ホームキャッシュの移行、会話・通知の読み込み、アカウント切替を確認する。
- プロフィール編集の取得・保存・取得失敗時の再試行、ブックマークへの導線、本文の選択解除、変更した初期設定と更新のお知らせの表示・終了を確認する。

- Play経由の更新・起動・変更箇所の確認は配信後に行う。準備完了後の引き継ぎと結果の反映は[リリース手順](#リリース準備配布記録の手順)に従う。
- CIは既存のapp・Gradle・androidTestの変更パスで共通チェックを選択する。パス・コマンド・ツール版の見直し判断をコミットまたはPRの説明へ記録する。

## 今後の確認事項・候補の管理

今後の確認事項と次回以降の保守・機能追加・文書改善の候補は、[GitHub Issues](https://github.com/ponpokoo/MastodonClient/issues)で管理する。内容、優先順位、採用版、進捗、確認結果は各Issueにまとめ、この計画書には個別の一覧や進捗を重複して記載しない。新しい確認事項や候補もIssueに登録し、今回の更新へ採用した範囲だけを「現行のリリース対象版」に反映する。

## リリース準備・配布・記録の手順

Google Playでの配布と内部リリースノートの保管を基本とし、GitHub Releaseの作成は必須としない。
「準備」と「提出・配布後の結果反映」を分ける。commit・pushで準備を終えたら、提出待ちであることと次の操作を引き継ぐ。提出・配信の結果は、後から同じ内部ノートへ反映する。

### 準備：対象版と配布するソースを確定

1. 前回の内部ノートと、Play Consoleまたは利用者による確認結果を読み、ソースの比較元・実際の配布版・今回の対象版を決める。会話で受けた提出・配信の連絡が未反映なら、対象版を照合して先にノートへ反映する。不明な項目は推測せず、必要な情報だけを確認する。`app/build.gradle.kts`のversionName・versionCodeと、この文書の「現行のリリース対象版」を揃える。使用済みのversionCodeを再利用しない。版番号を上げる際は[更新のお知らせ](ui/settings-moderation.md#更新のお知らせ)も今回の版に合わせて更新する。
2. 比較元からの差分を確認し、今回の変更範囲と既知の制約を内部ノートにまとめる。仕様・設定・運用手順が変わる文書だけを更新し、Issueで管理する未採用の候補は今回含む変更と区別する。
3. Release用のAAB・APKを作成する前に、`WelcomeGuideDialog.kt`の`appUpdateNotice`を確認する。`versionCode`が`app/build.gradle.kts`の対象版と一致し、本文が前回の配布版からの主な変更点を利用者向けに説明していることを、手順2で確認した差分と照合する。版番号や本文が古ければ、更新してからビルドする。

   [開発ガイド](project-setup.md#ビルドと確認)に従って必要なテスト・Releaseビルド・端末確認を行う。AABと、直接配布する場合のAPKについて、版番号・署名・SHA-256を確認する。実施した構成と結果、未確認事項をノートに記録し、過去の版の結果を今回の結果として扱わない。
4. コード・成果物・計画書の対象版と変更内容を照合し、`git diff --check`と`git status`でコミット対象を確認する。内部ノート、生成APK/AAB、IDE設定、署名鍵・署名設定・認証情報をコミット対象から除外する。
5. コードと必要な文書をコミットし、配布するソースの完全なコミットSHAを内部ノートに記録してブランチをpushする。未コミットの変更を含めてビルドした場合は、その変更を含むコミットと成果物の対応を確認してから確定する。タグを付ける場合はこのコミットを対象とし、同じversionNameの別ビルドを区別できる名前を使う。

準備の完了報告には、AABと内部ノートの場所、対応コミット、CIの結果または実行中の状態、次に行う操作を短く記載する。提出前なら「準備完了・提出待ち」とする。CIが実行中なら、その確認も次の作業に残す。Play経由の更新確認は配信後に行う予定として区別し、今回のビルドや端末テストで解決していない問題と混ぜない。

### 提出・配布後の結果反映

6. 利用者が確認済みAABをPlay Consoleへ提出し、versionName・versionCode・配布トラックを照合する。提出・審査・配信の連絡を受けたら、対象版の内部ノートを開いて該当する状態を更新する。Consoleを直接確認できなくても、利用者が確認した結果は「利用者確認」と申告日を添えて記録できる。提出済みを公開済みとして扱わない。
7. 配信後に、Play経由のインストール・既存版からの更新と対象版の主要動作を[公開ワークフロー](google-play-publication-workflow.md)に従って確認する。結果と残る制約を同じノートへ反映する。公開状態・日時・配布範囲も、直接確認した内容または利用者の確認結果の範囲で記録する。
8. 結果を反映したノートを成果物と合わせてバックアップし、保管先と実施日をノートに残す。ZIPへノートを収録していた場合は、元のAABとSHA-256を維持して、更新後のノートを収録した日時付きZIPを作る。状態の記録だけなら再ビルド・追加のcommit・pushは不要。動作・契約・手順に誤りが見つかった場合は該当文書を修正し、継続対応はIssuesで管理する。

結果反映時は、確認済みの項目を更新し、残る作業を次のように区別する。

| 区切り | 次の作業 |
| --- | --- |
| 準備完了・提出待ち | 利用者がAABを提出し、提出結果を伝える。CIが実行中なら結果も確認する |
| 提出済み・審査／配信待ち | Consoleの状態が変わったら、対象トラックと確認結果を伝える |
| 配信中・Play動作確認待ち | Playから更新して、起動と変更箇所を確認する |
| 配布確認済み | 問題があればIssueで継続し、ノートと成果物を保管する |

たとえば「対象版のAABを製品版トラックへ提出した」「Playから更新して起動と今回の変更箇所を確認した」のような連絡から、確認できた項目を反映する。対象版が会話から一意に分かる場合は聞き直さない。同じ版番号の別ビルドがある場合や確認範囲が曖昧な場合だけ、成果物や操作を特定するために確認する。提出日時など一部が不明でも、確認済みの提出・動作結果を一律に「未確認」へ戻さない。

GitHubでも配布する場合は、そのReleaseの本文・タグ・添付成果物を別途照合する。公開済みタグは動かさない。配布済みコードや成果物の修正は、別のversionCodeで準備する。

### 内部リリースノートの保管

版ごとに`app/release/Nagisa-<versionName>-vc<versionCode>-release-notes.md`を作成し、同じノートへ準備から公開後の結果まで追記する。
この名前のノートは`.gitignore`で除外する。Git管理外のため、成果物と一緒に非公開の保管先へバックアップする。旧版の記録を計画書から移した場合も、移し漏れと参照先を確認して同じ保管先へバックアップする。過去版のノートは当時の記録として保持し、計画書へ更新履歴や検証結果を戻さない。

AABとノートをひとつにまとめる場合は、`app/release/Nagisa-<versionName>-vc<versionCode>-release-package-<日時>.zip`へAAB・同名のSHA-256ファイル・内部ノートを収録する。ZIPもGit管理外とし、外部バックアップは別途行う。

記録する内容は次の範囲とする。まだ行う時期でない操作は「提出待ち」「配信後に実施」と次の作業を記載し、確認できていない事実は「未確認」、実行しなかった検証は「未実施」と区別する。冒頭に現在の状態と次の作業を置き、結果の連絡を受けたら更新する。古い「未確認」を残したまま末尾へ追記するだけにしない。

- versionName・versionCode、比較元、対応するソースのコミットSHA、今回の変更内容。
- 成果物のファイル名・SHA-256、版番号と署名の確認結果。
- 検証した版・構成・日時・端末／OS・サーバー、結果、既知の制約と残るIssue。既存の調査記録はリンクで参照する。
- Playの提出・配布トラック・公開状況と確認日時・確認元（Console直接確認／利用者確認）、配信後の動作確認、次の作業、バックアップの保管先と実施日。実際の提出・公開日時が不明な場合は、申告日や確認日と区別する。

署名鍵、パスワード、トークン、他人の投稿などはノートへ記録しない。公開状態はPlay Consoleの直接確認または利用者による確認結果を根拠にし、pushやAAB作成だけから推測しない。
