## v2.1.0の変更と確認記録

比較元は公開版`v2.0.2`。
公開済み2.0.2の差し替えAPKに含まれる投稿詳細からの復帰修正は、今回の新規変更に含めない。

### 今回の変更内容

- 投稿メディア：添付後にメディアを1件ずつ先行アップロードし、送信率、サーバー処理中、ALT反映中の状態を添付タイルに表示する。投稿時はアップロードと最新ALTの反映完了を待つ。
- 投稿メディア：失敗した添付ごとに再試行とエラー詳細を表示する。サーバー処理の待機が長引いた場合はメディアIDを保持して再確認し、重複アップロードを避ける。下書きにもメディアIDを保存し、復元時に有効性を確認する。
- タイムライン：自分の投稿やブーストを新着件数に含めない。ブースト済みのアイコンを太くし、選択状態を分かりやすくする。
- Android通知：通知をタップして対象アカウントを開いた後、そのアカウントのAndroid通知をまとめて消す。他のアカウントの通知は残す。

### 確認状況

- メディア処理、タイムライン、Android通知の回帰テストを追加した。2026-09-29にDebug単体テスト163件が成功（失敗・エラー・スキップなし）。
- 2.1.0の署名付きReleaseビルドが成功。APKはapplication ID `io.github.ponpokoo.mastodonclient`、versionName `2.1.0`、versionCode `9`。APK Signature Scheme v2で署名を検証した。SHA-256: `ec2376f1ecbdd884809a9df3655938ad0e1cfea251003950c8b0ab30d1981c3b`。
- 2.1.0の変更内容は、利用者が実機確認を完了したと報告した。
- 変更一覧は公開版2.0.2から今回の配布版までの差分を基にしたもの。

## リリース用pushの手順

### push前：対象版と計画書を同時に更新

1. GitHub ReleasesとGitタグを確認し、比較元の公開版と今回の対象版を確定する。同名タグ・Releaseが既にある場合は先に扱いを決める。
2. `app/build.gradle.kts`のversionName・versionCodeを対象版にし、`docs/release-plan.md`の「現行のリリース対象版」を**この版へ切り替える**。公開前の状態は「準備中」と記し、以前の公開版の表や確認記録を現行版として残さない。
3. 比較元から今回のコミット候補までの差分を確認し、「今回の変更内容」「確認状況」「次回以降の候補」を更新する。今回含まれない変更を引き継がない。
4. `docs/project-setup.md`と`docs/ui-guidelines.md`などの版番号表記を確認する。旧版番号、`未公開`、`リリース準備`などの古い表現を文書内検索し、対象版と矛盾がないか確認する。公開状況の正本はこの文書に置く。
5. 必要なテスト・Releaseビルド・端末確認を行い、実施済みの結果と未確認事項を記録する。署名済みAPKの署名、APK内の版番号、SHA-256も確認する。未実施項目を確認済みと書かない。
6. リリースノートを今回の差分と検証結果から作り、既知の制約を明記する。
7. **コミット直前の必須確認**：コードの版番号、APKの版番号、計画書の現行対象版・変更内容・確認状況、関連文書の版番号が一致することを確認する。`git diff --check`と`git status`でコミット対象を確認し、IDE設定、署名鍵、パスワード、認証情報、生成APKを除外する。
8. コードと**更新済み計画書を同じリリース準備コミット**に含め、注釈付きタグを作成する。ブランチ、タグの順にpushする。計画書が旧版のままならpushしない。

### 公開後：計画書の状態を確定

9. GitHub ReleaseのPre-release設定、本文、添付APKを確認して公開する。公開しただけではリリース作業を完了としない。
10. 公開ページでタグの対象コミットと添付APKのSHA-256を確認する。「現行のリリース対象版」の状態・公開日・Releaseリンクを確定し、準備中・未公開の表現が残っていないか検索する。
11. 公開後の文書修正を別コミットでブランチへpushする。**公開済みタグは動かさない**。最後に計画書の現行版とGitHub Releaseの版が一致することを確認する。

公開前に作業を止めた場合は、計画書の状態を「準備中」のままにし、公開済みとは記さない。
