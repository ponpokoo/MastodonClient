## 次回更新の実装順序

次回の版番号は、内容が決まりリリース作業を始める時点で決める。現時点では、
正式版ではなく次のベータ版を前提に、以下を順に個別実装・確認する。

1. リアルタイム通知（実装・実機確認済み）
2. 通知欄の更新・既読・重複防止・表示位置の改善（実装・実機確認済み）
   - 通知タブ表示時と表示中のアプリ復帰時の自動更新は実装済み。
   - 自動更新とStreaming受信の競合時はIDで統合し、重複と消失を防止する。
   - 既読の見せ方、通知タップ時の詳細動作、スクロール位置の追加確認は未実施。
3. Android共有メニューからのURL・画像受信（実装・実機確認済み）
4. お気に入り・ブーストのOptimistic UI Update（実装・実機確認済み）
   - 操作直後にアイコンと件数を更新し、API失敗時は操作前の状態へ戻してエラーを表示する。
   - 同一投稿の通信中操作を抑止し、タイムライン、検索、通知、プロフィール、詳細、
     ハッシュタグ、お気に入り・ブックマーク一覧へ状態を同期する。
5. お気に入りアイコン長押しによるユーザー一覧（実装・実機確認済み）
   - お気に入り数が1件以上の投稿では、アイコン長押しでアカウント一覧を開く。
   - 一覧から選んだアカウントはプロフィール画面へ移動する。

各項目はテストと個別確認が終わるまで次へ進まない。正式リリース用のUI解説、
設定画面構成、デザインの総合確認はこの5項目の後の候補とする。

### リアルタイム通知の方式決定

- 前景中はアカウントごとにMastodon Streaming APIのユーザーストリームを1本接続し、
  `notification` イベントを通知欄と未読数に即時反映する。同じ接続をタイムライン更新にも使う。
- 接続先はインスタンス情報の `configuration.urls.streaming` を優先し、なければインスタンスURLを使う。
- 異常終了とサーバー側の正常EOFのどちらでも、前景中は最大30秒間隔で再接続する。
- 初期設定ではバックグラウンド移行時に接続を停止する。バックグラウンドのOS通知は
  JobSchedulerによる約15分ごとの簡易取得とし、即時到着は保証しない。
- 常時接続のフォアグラウンドサービスは、電池消費と常駐通知を避けるため採用しない。
  バックグラウンド即時通知はMastodon Web PushとAndroid向け中継サービスを将来候補とする。

調査根拠: [Mastodon Streaming API](https://docs.joinmastodon.org/methods/streaming/),
[Mastodon Push API](https://docs.joinmastodon.org/methods/push/),
[Android バックグラウン実行の概要](https://developer.android.com/develop/background-work/background-tasks)

## 次回ベータの完了条件

- 実装内容と未実装事項を `docs/ui-guidelines.md` に反映する。
- 該当する単体テストを追加・更新し、`testDebugUnitTest` を成功させる。
- `assembleDebug` と `assembleDebugAndroidTest` を成功させる。
- 変更範囲に応じた実機確認を行い、端末・Androidバージョン・確認結果を記録する。
- 配布する場合は、版番号を前回より増やし、`assembleRelease` でAPKを生成する。
- `apksigner verify --verbose --print-certs` とAPK内部のversionCode／versionNameを確認する。
- リリースノートに変更点、確認済み事項、未確認事項、既知の問題を分けて記載する。

```text

主な変更
-

確認結果
- 単体テスト:
- APK署名:
- 実機確認:

未確認事項・既知の問題
-

インストール方法
Assetsの app-release.apk をダウンロードしてインストールしてください。
```

リリース作成前に、GitHub上の前回Releaseのタグ・添付APK・プレリリース状態を確認する。
未追跡のIDE設定、署名鍵、パスワード、認証情報はコミット・添付・リリースノートに含めない。
