#### 音声・動画の再生

- 音声の自動再生は行わず、再生操作からプレイヤーを生成する。再生終了後は先頭から再再生でき、エラー時は再試行できる。
- 音声・全画面動画にはMedia3／ExoPlayerを使用する。再生元は添付本体のURLとし、プレビュー画像のURLへ代替しない。
- シークは操作終了時に確定し、一時停止中は位置だけを変更する。長さ不明・シーク非対応・エラー時はシークを無効化する。音量はプレイヤー単位で調整し、端末の音量設定は変更しない。
- 音声の投稿者アイコンに再生操作を重ね、左右に秒送り、下部に時間・シーク・上方向に開く音量バーを配置する。
- 全画面動画の横画面操作部は下端の1列にまとめ、映像のタップで上部・下部の操作UIを表示／非表示にする。カメラ穴・切り欠きの安全領域と、音量操作中のボタン位置を考慮する。
- 投稿内の自動再生動画・GIF動画に停止・再開ボタンを追加する。動画部分のタップは全画面表示へ移動する。
- 別の音声・全画面動画の再生、画面外への移動、背景移行では一時停止し、戻っただけでは再開しない。破棄時にプレイヤーを解放する。

実装経路と段階ごとの検証結果は[音声添付の調査・修正記録](audio-playback.md)を参照する。

### 下書き保存後の送信

2026-10-03に、添付なしのYouTube URLを含む投稿について、通常送信よりも下書き保存・復元後の送信で、投稿画面が閉じてから相手側に表示されるまでが遅いとの報告を受けた。原因は未確定。2026-10-03のリリース依頼で、ユーザーから未確認の実機項目は確認済みとの報告を受けた。送信動作は確認済みとし、原因の特定や配送時間の測定は別の調査として扱う。

- 同じ投稿元・受信先・公開範囲・言語・CW・返信／引用指定で通常送信と下書き保存・復元後の送信を比較する。YouTube URLあり・URLなしを分けて確認する。
- 使用APKとサーバーの版を記録し、API応答、投稿画面が閉じた時点、受信先への到着、相手側への表示の時刻を分けて、通信・サーバー配送・受信側更新のどこで遅れるか確認する。
- 送信失敗後に同じ画面で別の下書きを復元した場合のIdempotency-Key再利用も、配送遅延とは別の確認事項として扱う。

[原因調査報告](investigations/draft-post-latency-report.md)では、調査時点の作業ツリーで通常・下書きのHTTP本文の一致と、予約日時が送信されないことをローカル検証した。実サーバーでの配送時間はこの調査では未測定。今回の実機確認済み報告と、原因特定・不具合修正の記録は区別する。

## 作業ツリーの検索修正（2026-10-04）

検索は投稿・アカウント・ハッシュタグの選択対象だけを取得する。入力だけでは通信せず、キーボードの検索キーで開始する。検索後のタブ切り替えは未取得の対象を取得し、同じ検索語の取得済み結果は再利用する。検索専用の通信設定は読み取り30秒・全体45秒とし、初回・追加取得は20件ずつ要求する。

検索バーは探索と検索で共通とし、戻る操作では入力を保持する。文字がある間だけ表示する×ボタンは、変換中の文字も消して探索へ戻る。検索結果の3タブは左右のスワイプで切り替える。追加取得の失敗時は表示済みの結果を残して再試行でき、検索語・対象・アカウントを変更した後に古い応答を反映しない。

## リリース用pushの手順

### push前：対象版と計画書を同時に更新

1. GitHub ReleasesとGitタグを確認し、比較元の公開版と今回の対象版を確定する。同名タグ・Releaseが既にある場合は先に扱いを決める。
2. `app/build.gradle.kts`のversionName・versionCodeを対象版にし、`docs/release-plan.md`の「現行のリリース対象版」を**この版へ切り替える**。以前の公開版の表や確認記録を現行版として残さない。公開状況欄は今回のタグに対応するGitHub Releaseへの参照とし、公開状態は記載しない。
3. 比較元から今回のコミット候補までの差分を確認し、「今回の変更内容」「確認状況」「次回以降の候補」を更新する。今回含まれない変更を引き継がない。
4. `docs/project-setup.md`と`docs/ui-guidelines.md`などの版番号表記を確認する。旧版番号や古い確認記録を文書内検索し、対象版と矛盾がないか確認する。対象版・変更内容・確認結果はこの文書、公開状態・公開日・Pre-release区分はGitHub Releaseを正本とする。
5. 必要なテスト・Releaseビルド・端末確認を行い、実施済みの結果と未確認事項を記録する。署名済みAPKの署名、APK内の版番号、SHA-256も確認する。未実施項目を確認済みと書かない。
6. リリースノートを今回の差分と検証結果から作り、既知の制約を明記する。
7. **コミット直前の必須確認**：コードの版番号、APKの版番号、計画書の現行対象版・変更内容・確認状況、関連文書の版番号が一致することを確認する。`git diff --check`と`git status`でコミット対象を確認し、IDE設定、署名鍵、パスワード、認証情報、生成APKを除外する。
8. コードと**更新済み計画書を同じリリース準備コミット**に含め、注釈付きタグを作成する。ブランチ、タグの順にpushする。計画書が旧版のままならpushしない。

### 公開・公開後：配布内容の一致を確認

9. GitHub ReleaseのPre-release設定、本文、添付APKを確認して公開する。公開しただけではリリース作業を完了としない。
10. 公開ページでPre-release設定、版番号、タグの対象コミット、添付APKのSHA-256を確認し、リリース用push前に確定した計画書・配布候補と一致すればリリース作業を完了とする。公開状態や公開日を計画書へ転記するための追加コミット・pushは行わない。
11. 誤記や不一致があった場合のみ、該当する文書やGitHub Releaseを修正して再確認する。文書を修正した場合は別コミットでブランチへpushする。**公開済みタグは動かさない**。コードやAPKの修正が必要なら、別バージョンのリリースとして扱う。

公開前に作業を止めた場合も、計画書に公開済みとは記さない。Releaseリンクの記載だけでは公開を意味せず、公開状況はGitHub Releaseで確認する。
