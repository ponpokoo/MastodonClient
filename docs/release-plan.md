## 次回更新の候補

次回の版番号は、内容が決まりリリース作業を始める時点で決める。現時点では、
正式版ではなく次のベータ版を前提に以下を優先度順で検討する。

1. 正式リリース用のUI解説
   - 初回利用者が4タブ、投稿、タイムライン切替、設定、画面タイトルのタップによる先頭移動を理解できる内容にする。
   - アプリ内画面、README、GitHub Releasesのどこを正本にするかを決めてから実装する。
2. 設定画面構成
   - 現在の単一画面の項目を、利用頻度と機能のまとまりに基づいて見直す。
   - 既存のDataStoreキーと初期値を壊さない移行・確認方法を用意する。
3. リアルタイム通知
   - 前景中のストリーミング、約15分ごとの簡易通知、将来のプッシュ通知を区別して要件を定義する。
   - バックグラウンドで即時到着を保証する機能は未実装であることを、仕様とUIで明示する。
4. デザインの修正
   - 文字倍率、ライト／ダーク表示、48 dp以上のタップ領域、読み上げ、コントラストを実機で確認する。
   - 修正対象と判断基準を画面単位で記録し、見た目だけの変更と操作性の変更を分ける。

## 次回ベータの完了条件

- 実装内容と未実装事項を `docs/ui-guidelines.md` に反映する。
- 該当する単体テストを追加・更新し、`testDebugUnitTest` を成功させる。
- `assembleDebug` と `assembleDebugAndroidTest` を成功させる。
- 変更範囲に応じた実機確認を行い、端末・Androidバージョン・確認結果を記録する。
- 配布する場合は、版番号を前回より増やし、`assembleRelease` でAPKを生成する。
- `apksigner verify --verbose --print-certs` とAPK内部のversionCode／versionNameを確認する。
- リリースノートに変更点、確認済み事項、未確認事項、既知の問題を分けて記載する。

## リリースノートのひな形

```text
Nagisa x.y.z のベータ版です。

主な変更
-

確認結果
- 単体テスト:
- APK署名:
- 実機確認:

未確認事項・既知の問題
-

インストール方法
Assetsの app-release.apk をダウンロードしてインストールしてください。
```

リリース作成前に、GitHub上の前回Releaseのタグ・添付APK・プレリリース状態を確認する。
未追跡のIDE設定、署名鍵、パスワード、認証情報はコミット・添付・リリースノートに含めない。
