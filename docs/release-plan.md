## 0.1.1の変更内容

### 通知

- 通知タブ表示時とアプリ復帰時に自動更新する。
- 自動更新では更新アイコンを表示せず、手動の引っ張って更新でのみ表示する。
- 自動更新で新着を取得した場合は一覧の先頭へ移動し、新着がなければ表示位置を維持する。
- 自動更新と手動更新を区別するテストを追加する。
- 閲覧中アカウントのStreaming通知を、通知タブに加えてAndroid通知にも表示する。
- 通知設定に「起動中の通知」を追加し、バックグラウンドの簡易通知とは独立して切り替え可能にする。
- 簡易通知と配信済みIDを共有して二重通知を抑止し、アカウント切替や背景移行後の遅延配信も抑止する。
- 詳細・設定画面でも受信を続けるため、前景判定をActivity単位にする。

### 投稿・タイムライン

- Mastodon APIの`in_reply_to_id`と`in_reply_to_account_id`を取得・保持する。
- 返信投稿に返信先アカウントを表示し、タップ時は対象アカウントのプロフィールへ移動する。
- 自分自身への返信でメンション情報がない場合は、自分のアカウントIDを補完する。
- API変換テストとCompose UIテストを追加する。
- 投稿画面の操作ボタンに表示・非表示設定を追加し、初期状態では全操作を表示する。

### 設定

- 設定をカテゴリ一覧と詳細画面の2階層に整理。
- 「ストレージ」に画像キャッシュ削除を追加。アカウント・設定・下書きは保持する。
- 「このアプリについて」にバージョン名とビルド番号を表示。
- 投稿・タイムラインの操作順設定にアイコンを表示し、上下ボタンをドラッグハンドルへ変更。
- 並び替えは指を離したときに保存。読み上げのカスタム操作からも上下に移動できる。

### プロフィール

- ユーザーID直下に投稿・フォロー・フォロワー・登録日を一列で配置。
- プロフィール項目を見出しなしの欄にまとめ、区切り線で整理。確認済みリンクは右端のチェックで表示。
- 「フォローされています」はID横に収まる場合はID横、収まらない場合は表示名横へ配置。
- 三点メニューのポップアップをボタン自体を基準に表示。
- プロフィール画像と三点ボタンの配置は従来の位置を維持。

### デザイン

- ダーク背景をわずかに紫がかったグレーへ変更し、アクセントを淡い青・青灰色へ調整。
- 背景、一覧、下部ナビゲーション、メニュー・ダイアログに控えめな明度差を設定。
- ライトテーマは維持。

## リリース前の完了条件

- 実装内容と未実装事項を `docs/ui-guidelines.md` に反映する。
- 未カバーの振る舞い・回帰に必要なテストのみ追加・更新し、配布候補で`testDebugUnitTest`を成功させる。
  日常の変更は開発ガイドに従って対象を絞り、文書更新ではGradleを実行しない。
- 端末テスト用APKが必要な場合だけ`assembleDebugAndroidTest`を実行する。
  配布確認用のRelease APKがある場合、同じ目的のDebug APK生成を必須にしない。
- 変更した機能に必要な端末確認を行い、端末・Androidバージョン・対象版・結果を記録する。
- 配布する場合は、版番号を前回より増やし、`assembleRelease` でAPKを生成する。
- `apksigner verify --verbose --print-certs` とAPK内部のversionCode／versionNameを確認する。
- APKのSHA-256を記録する。
- GitHub Releasesのタグ、プレリリース設定、添付APKを確認する。
- リリースノートに変更点、確認済み事項、未確認事項、既知の問題を分けて記載する。

未追跡のIDE設定、署名鍵、パスワード、認証情報はコミット・添付・リリースノートに含めない。

## リリース用pushの手順

リリース用のコミットとタグをpushする前に、次の順序でこの文書を更新する。

1. GitHub ReleasesとGitタグを確認し、比較元となる前回公開版を確定する。
2. 前回公開版から配布候補までの差分を確認し、「変更内容」を実際に含まれる機能だけで書き直す。
   過去の計画項目や、今回の差分に含まれない変更は引き継がない。
3. `versionName`と`versionCode`を確定し、この文書の対象版と一致させる。
4. 配布候補に対して必要な単体テスト、ビルド、実機確認を実行する。
5. 配布APKの署名、APK内の版番号、SHA-256を確認する。
6. 実際に確認できた結果だけを「確認結果」へ記録し、未確認事項と既知の制約を更新する。
7. 「リリースノート案」を変更内容と確認結果に合わせて確定する。
8. `git diff`と`git status`でコミット対象を確認し、IDE設定、署名情報、生成物などが含まれていないことを確認する。
9. コードと更新済みのリリース計画を同じリリースコミットに含め、注釈付きタグを作成する。
10. ブランチをpushした後にタグをpushし、GitHub Releasesの本文、公開区分、添付APKを最終確認する。

テスト、署名、実機確認などを実行していない場合は、以前の結果を今回の確認結果として転記しない。
同名タグがすでにリモートに存在する場合は、通常のpushを続行せず、公開済みReleaseへの影響を確認してから
タグを維持するか、別の版番号に進めるかを決める。
