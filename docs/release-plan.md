## v2.1.2の変更と確認記録

比較元は公開版`v2.1.1`。比較元から今回のリリース準備コミットまでの変更を対象とする。
2.1.1に含まれる投稿言語・ハッシュタグ・アイコン形状設定・通知キャッシュなどは、新規変更として再掲しない。

### 今回の変更内容

#### 引用・返信

- ブーストの長押しメニューで、サーバー標準の「引用」と「引用（リンク）」を選べるようにする。標準の引用情報がない投稿ではリンク方式だけを表示し、標準の引用はサーバーの許可・承認条件に従う。
- 選んだ引用方式を投稿画面へ引き継ぐ。標準の引用は引用元投稿IDを送信し、リンク方式は本文へ投稿URLを挿入する。同じ投稿でも方式ごとに一時入力・保存済み下書きを分けて保持する。
- 返信・引用のプレビューに「×」を追加する。元の投稿の読み込み前でも解除でき、本文のメンション・URL、CW、添付などは保持する。引用を解除すると、引用に伴うメディア・投票・投稿元切替の制限も解除する。
- リンク方式では、本文から引用元URLを削除・置換すると引用指定とプレビューを解除する。URLを再入力しても引用指定は復活させない。標準の引用は本文中のURL削除では解除しない。
- 引用元のプレビューも取得済み投稿を再利用し、キャッシュがない場合は投稿単体を取得する。解除・下書き呼出・アカウント切替後に遅れて届いた取得結果や失敗を反映しない。

#### ホームのスクロール

- ホーム表示中に下部のホームアイコンを押した際、スクロールが途中で止まる場合に先頭の投稿・オフセット0へ補正する。新着件数のタップと、更新後に先頭へ戻る設定にも適用する。
- 移動中にスワイプした場合はユーザーの操作を優先し、先頭へ強制的に戻さない。

#### リアクション表示・設定プレビュー

- タイムライン表示設定に「リアクションを表示」を追加する。初期値はオンで、投稿に付いた絵文字リアクション一覧を非表示にできる。リアクション操作ボタンの表示設定とは独立し、従来の保存設定でもオンを既定値として読み込む。
- カスタム絵文字リアクションは元画像のURLを優先してGIFのアニメーションを表示する。元画像URLが未指定・空白の場合は静止画URLへフォールバックする。
- 設定プレビューのユーザーアイコンにアプリアイコンを表示し、サンプルのリアクションも追加する。お気に入りやリアクションの操作から、実際のアカウント一覧を開かないようにする。

#### 文書・リリース手順

- アプリ紹介、インストール・初回設定、既知の制約、不具合報告の案内をREADMEに追加する。
- Firebase設定・Push購読・受信と復号・Relay契約・Workers運用の文書を整理し、既存実装との説明のずれを修正する。PushやRelayの新機能追加ではない。
- 単純なUI設定はComposeから設定Storeを直接利用できる例外を、実装規則と開発ガイドに明記する。
- リリース計画はpush前に対象版・変更内容・確認結果を確定し、公開状態・公開日・Pre-release区分はGitHub Releaseを参照する運用へ変更する。公開後は配布内容の一致を確認し、誤記がなければ追加の文書pushを行わない。

### 確認状況

- 引用方式の下書き復元・送信内容・一時入力の分離、返信・引用解除後の遅延応答を対象とする単体テストを追加した。
- リアクション表示設定の保存・旧設定との互換性、元画像URL優先と静止画へのフォールバックを対象とする単体テストを追加した。
- 引用メニュー、返信・引用の解除、ホームの先頭移動と操作による中断、リアクション表示切替、設定プレビューの端末テストを追加・更新した。

### 公開前の手動確認

- 今回の署名付きRelease APKそのものの端末インストール・操作確認と、実際のアカウントでの確認は未実施。2.1.1の手動確認を今回の結果として引き継がない。
- 引用対応・非対応サーバーでの引用方式と送信結果、返信・引用解除後の通常投稿、ホームの先頭移動、リアクション表示切替・GIF表示、設定プレビューを配布候補で確認する。

### 既知の制約

- 標準の引用はサーバーの対応と引用許可に依存する。非対応サーバーでは投稿URLがある場合にリンク方式を利用する。
- リアクション表示は対応サーバーの投稿が対象。GIF自動再生の設定は投稿メディア用で、カスタム絵文字のアニメーションを個別に制御しない。
- DB保存の対象は通知のみ。ホーム・ローカル・連合の永続保存と、表示データ全体をDB中心にする移行は次回以降の候補とする。
- 通知の200件は端末保存の上限であり、オンラインで閲覧できる履歴の上限ではない。画像本体は通知DBへ保存しない。
- [通知の端末保存](ui-guidelines.md#通知の端末保存試験導入)は試験導入。表示速度・保存容量などの評価は、次回以降のDB化範囲を決める材料とする。

## リリース用pushの手順

### push前：対象版と計画書を同時に更新

1. GitHub ReleasesとGitタグを確認し、比較元の公開版と今回の対象版を確定する。同名タグ・Releaseが既にある場合は先に扱いを決める。
2. `app/build.gradle.kts`のversionName・versionCodeを対象版にし、`docs/release-plan.md`の「現行のリリース対象版」を**この版へ切り替える**。以前の公開版の表や確認記録を現行版として残さない。公開状況欄は今回のタグに対応するGitHub Releaseへの参照とし、公開状態は記載しない。
3. 比較元から今回のコミット候補までの差分を確認し、「今回の変更内容」「確認状況」「次回以降の候補」を更新する。今回含まれない変更を引き継がない。
4. `docs/project-setup.md`と`docs/ui-guidelines.md`などの版番号表記を確認する。旧版番号や古い確認記録を文書内検索し、対象版と矛盾がないか確認する。対象版・変更内容・確認結果はこの文書、公開状態・公開日・Pre-release区分はGitHub Releaseを正本とする。
5. 必要なテスト・Releaseビルド・端末確認を行い、実施済みの結果と未確認事項を記録する。署名済みAPKの署名、APK内の版番号、SHA-256も確認する。未実施項目を確認済みと書かない。
6. リリースノートを今回の差分と検証結果から作り、既知の制約を明記する。
7. **コミット直前の必須確認**：コードの版番号、APKの版番号、計画書の現行対象版・変更内容・確認状況、関連文書の版番号が一致することを確認する。`git diff --check`と`git status`でコミット対象を確認し、IDE設定、署名鍵、パスワード、認証情報、生成APKを除外する。
8. コードと**更新済み計画書を同じリリース準備コミット**に含め、注釈付きタグを作成する。ブランチ、タグの順にpushする。計画書が旧版のままならpushしない。

### 公開・公開後：配布内容の一致を確認

9. GitHub ReleaseのPre-release設定、本文、添付APKを確認して公開する。公開しただけではリリース作業を完了としない。
10. 公開ページでPre-release設定、版番号、タグの対象コミット、添付APKのSHA-256を確認し、リリース用push前に確定した計画書・配布候補と一致すればリリース作業を完了とする。公開状態や公開日を計画書へ転記するための追加コミット・pushは行わない。
11. 誤記や不一致があった場合のみ、該当する文書やGitHub Releaseを修正して再確認する。文書を修正した場合は別コミットでブランチへpushする。**公開済みタグは動かさない**。コードやAPKの修正が必要なら、別バージョンのリリースとして扱う。

公開前に作業を止めた場合も、計画書に公開済みとは記さない。Releaseリンクの記載だけでは公開を意味せず、公開状況はGitHub Releaseで確認する。
