## v2.1.1の変更と確認記録

比較元は公開版`v2.1.0`。2.1.0に含まれるメディア先行アップロードなどを新規変更として再掲しない。

### 今回の変更内容

#### 投稿・返信

- 投稿言語を選ぶボタンと中央ダイアログを追加する。「デフォルト」は言語指定を省略してサーバーに委ねる。選択した言語は下書き・一時入力に保持し、投稿編集では元の言語を引き継ぐ。
- ハッシュタグボタンを追加し、本文のカーソル位置に半角の`#`を挿入する。言語・ハッシュタグの操作もボタン順序と表示・非表示の設定に対応する。
- 返信元のプレビューに同じアカウント・インスタンスの取得済み投稿を再利用し、投稿設定や絵文字の取得を待たずに表示する。キャッシュがない場合は返信元の投稿単体を取得する。
- 返信相手のメンションを本文から削除すると、返信元のプレビューと返信先指定を解除して通常投稿へ切り替える。本文クリアでも同じように解除し、メンションの再入力だけでは返信を復活させない。
- 返信中に投稿元アカウントを切り替える場合は、本文とメンションを引き継ぎ、返信先指定を解除する。添付などは切替元の一時入力に保持し、別アカウントへ送信しない。
- 返信先の読み込みが完了する前の投稿を防ぎ、返信解除・アカウント切替後に遅れて届いた返信元の取得結果を反映しない。

#### 一覧・詳細・表示設定

- ユーザーアイコンの形を丸／四角（角丸なし）から選べるようにする。投稿一覧、プロフィール、通知者・通知内の投稿者、設定プレビューに反映する。初期値は丸。
- 1年以上前の投稿日時に年を表示する。判定と日付表示は端末のタイムゾーンに従う。
- 会話詳細を開いた際、会話取得後に選択した投稿を画面中央へ配置する。画面より長い投稿は先頭を表示し、手動スクロール後・画面への復帰・反応更新・再取得では位置を移動し直さない。
- 引っ張って更新の発動までに必要な指の移動量を従来の約3分の2に調整し、インジケーターの移動距離は維持する。
- 保存済みの投稿ボタン設定に未対応の操作が含まれていても、他の設定を読み込めるようにする。追加した操作は既存の並び順を維持して補う。

#### 通知・端末保存

- Android通知の消去をアプリ内の既読判定に合わせる。選択中のフィルターで既読になった取得済み通知だけを消し、別アカウントや対象外の通知は残す。通知タップだけでアカウント全体を一括消去しない。
- 既読にした通知を配信履歴へ記録し、遅れて届いた同じ通知の再表示を抑止する。アイコン画像の読み込み完了によって消去済み通知が再表示される競合も防ぐ。
- 通知のみRoomの永続キャッシュを試験導入する。アカウント・インスタンス別に最新200件と既読位置を保存し、起動・アカウント切替時は保存済み一覧を先に表示してから通信更新する。
- 起動時の更新成功後は最新ページに置き換え、古い保存履歴との間の未取得通知を通常の追加取得で遡れるようにする。更新中のStreaming通知は保持し、更新失敗時は保存済み一覧を残して自動では既読にしない。
- 通知取得・追加取得・Streaming受信・通知内の投稿操作を保存内容へ反映する。DBの読み書きに失敗しても通信と表示を継続し、既読位置の通信取得に失敗した場合は端末の保存値を使う。
- ログアウト時に対象アカウントの通知キャッシュを削除し、遅延した読み書きで復活しないようにする。通知DBはバックアップ・端末移行から除外する。

### 既知の制約

- DB保存の対象は通知のみ。ホーム・ローカル・連合の永続保存と、表示データ全体をDB中心にする移行は次回以降の候補とする。
- 通知の200件は端末保存の上限であり、オンラインで閲覧できる履歴の上限ではない。画像本体は通知DBへ保存しない。
- [通知の端末保存](ui-guidelines.md#通知の端末保存試験導入)は試験導入。表示速度・保存容量などの評価は、次回以降のDB化範囲を決める材料とする。

## リリース用pushの手順

### push前：対象版と計画書を同時に更新

1. GitHub ReleasesとGitタグを確認し、比較元の公開版と今回の対象版を確定する。同名タグ・Releaseが既にある場合は先に扱いを決める。
2. `app/build.gradle.kts`のversionName・versionCodeを対象版にし、`docs/release-plan.md`の「現行のリリース対象版」を**この版へ切り替える**。公開前の状態は「準備中」と記し、以前の公開版の表や確認記録を現行版として残さない。
3. 比較元から今回のコミット候補までの差分を確認し、「今回の変更内容」「確認状況」「次回以降の候補」を更新する。今回含まれない変更を引き継がない。
4. `docs/project-setup.md`と`docs/ui-guidelines.md`などの版番号表記を確認する。旧版番号、`未公開`、`リリース準備`などの古い表現を文書内検索し、対象版と矛盾がないか確認する。公開状況の正本はこの文書に置く。
5. 必要なテスト・Releaseビルド・端末確認を行い、実施済みの結果と未確認事項を記録する。署名済みAPKの署名、APK内の版番号、SHA-256も確認する。未実施項目を確認済みと書かない。
6. リリースノートを今回の差分と検証結果から作り、既知の制約を明記する。
7. **コミット直前の必須確認**：コードの版番号、APKの版番号、計画書の現行対象版・変更内容・確認状況、関連文書の版番号が一致することを確認する。`git diff --check`と`git status`でコミット対象を確認し、IDE設定、署名鍵、パスワード、認証情報、生成APKを除外する。
8. コードと**更新済み計画書を同じリリース準備コミット**に含め、注釈付きタグを作成する。ブランチ、タグの順にpushする。計画書が旧版のままならpushしない。

### 公開後：計画書の状態を確定

9. GitHub ReleaseのPre-release設定、本文、添付APKを確認して公開する。公開しただけではリリース作業を完了としない。
10. 公開ページでタグの対象コミットと添付APKのSHA-256を確認する。「現行のリリース対象版」の状態・公開日・Releaseリンクを確定し、準備中・未公開の表現が残っていないか検索する。
11. 公開後の文書修正を別コミットでブランチへpushする。**公開済みタグは動かさない**。最後に計画書の現行版とGitHub Releaseの版が一致することを確認する。

公開前に作業を止めた場合は、計画書の状態を「準備中」のままにし、公開済みとは記さない。
