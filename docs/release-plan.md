### 2.5.7で追加する変更

- ホーム・ローカル・連合の新着案内を共通化する。途中を閲覧中は「↑ 新着○件」の件数・文言を固定し、追加データは取り込み続ける。先頭への到着後は約0.6秒、先頭での受信結果は約1.8秒表示する。復元時は「↑ 前回の位置を表示中」から最新側へ移動でき、エラーや操作結果は案内と並べて表示する。詳細は[新着案内とメッセージ](ui-guidelines.md#新着案内とメッセージ)に従う。
- 通知をアカウントの有効化時に先行取得し、タブを開いた際は取得済みの一覧を表示しながら更新する。読み込み中に重なる更新要求をまとめ、表示開始時の新着背景を維持する。通知欄の「新着○件」は閲覧位置によらず約1.8秒表示し、先頭への移動操作は付けない。詳細は[通知の表示・更新・既読位置](ui/notifications.md#通知の表示更新既読位置)に従う。
- ログイン・アカウント追加のサーバー入力にドメイン候補を追加する。登録済みの接続先・公式一覧・同梱候補を統合し、取得失敗時も手入力を続けられるようにする。候補選択後も明示的な接続確認を必要とする。詳細は[サーバードメインの入力候補](ui/accounts-profile.md#サーバードメインの入力候補)に従う。
- 絵文字検索のクリア時にカテゴリと入力フォーカスを保持し、シートの高さ・キーボード表示時の余白・閉じる操作を調整する。ホームのリアクションピッカーは標準の半開き・展開・縮小に対応し、投稿画面と他画面ではヘッダーを引いて閉じる。投稿画面・設定の操作名を「絵文字」に統一する。詳細は[絵文字ピッカー](ui/emoji-picker.md)に従う。
- 投稿元アプリ名に有効なWebサイトURLがある場合は、従来の外観を保ったままリンクとして開けるようにする。新規OAuth登録のWebサイトURLをGoogle Play掲載ページへ変更する。保存済み登録は維持する。
- 投稿送信ボタンの色・押下時の背景と影を調整し、投稿操作アイコンと件数の間隔、押下ハイライトの大きさを整える。

2.5.6までの長文省略・リアクションした投稿・APNG絵文字・お気に入り・投稿ボタン配置などの機能は引き継ぐ。現在の操作仕様は[UI・機能仕様](ui-guidelines.md)、過去版の変更履歴は各版の内部ノートを参照する。

### 2.5.7の配布前に確認すること

現在はクローズドテスト中で、深刻な問題は報告されていない。今回の変更箇所を中心に、以下の代表的な操作と自動検証を確認する。すべての条件を手動で繰り返す必要はない。同じコード・構成の成功済み結果を参照し、今回の確認結果・残る制約は内部リリースノートへ記録する。

- 新着案内の件数固定・追加受信・先頭到着後の消失と、通知欄の短時間表示を確認する。復元・エラーとの同時表示・既読や同一IDの再取得などは、関係する既存の回帰テストも使う。
- サーバー候補の選択、絵文字の検索・消去・開閉、投稿元アプリ名のリンク、投稿送信ボタンと操作アイコンの押下を確認する。全テーマ・全サーバーで同じ操作を繰り返さず、変更に影響する条件を選ぶ。
- 配布候補の単体テスト全体・Release lint・R8適用済みビルドと、APK・AABの版番号・署名・SHA-256を確認する。今回のコードで成功済みなら再実行しない。
- Playで配信されたら、既存版からの更新・起動・今回の変更箇所を短く確認する。認証やDB移行などへの変更、保存データの不具合報告がある場合は、その範囲の確認を追加する。提出と正式公開後の更新は[公開ワークフロー](google-play-publication-workflow.md)に従う。
- CIは既存のapp・Gradle・androidTestの変更パスで共通チェックを選択する。パス・コマンド・ツール版の見直しが必要か確認し、コミットまたはPRの説明へ記録する。

## リリース準備・配布・記録の手順

Google Playでの配布と内部リリースノートの保管を基本とし、GitHub Releaseの作成は必須としない。
ソースのcommit・pushと、Playへの提出・公開は別の作業として確認する。

### 準備：対象版と配布するソースを確定

1. 前回の配布版の内部ノートとPlay Consoleを確認し、比較元と今回の対象版を決める。`app/build.gradle.kts`のversionName・versionCodeと、この文書の「現行のリリース対象版」を揃える。使用済みのversionCodeを再利用しない。
2. 比較元からの差分を確認し、今回の変更範囲と既知の制約を内部ノートにまとめる。仕様・設定・運用手順が変わる文書だけを更新し、次回以降の候補は今回含む変更と区別する。
3. [開発ガイド](project-setup.md#ビルドと確認)に従って必要なテスト・Releaseビルド・端末確認を行う。AABと、直接配布する場合のAPKについて、版番号・署名・SHA-256を確認する。実施した構成と結果、未確認事項をノートに記録し、過去の版の結果を今回の結果として扱わない。
4. コード・成果物・計画書の対象版と変更内容を照合し、`git diff --check`と`git status`でコミット対象を確認する。内部ノート、生成APK/AAB、IDE設定、署名鍵・署名設定・認証情報をコミット対象から除外する。
5. コードと必要な文書をコミットし、配布するソースの完全なコミットSHAを内部ノートに記録してブランチをpushする。未コミットの変更を含めてビルドした場合は、その変更を含むコミットと成果物の対応を確認してから確定する。タグを付ける場合はこのコミットを対象とし、同じversionNameの別ビルドを区別できる名前を使う。

### 配布・公開後：実際の結果を記録

6. 確認したAABをPlay Consoleへ提出し、versionName・versionCode・配布トラックを照合する。提出日時、テスト配布、審査、公開の状態は、実際に確認できた段階まで内部ノートに記録する。提出済みを公開済みとして扱わない。
7. Play経由のインストール・既存版からの更新と、対象版の主要動作を[公開ワークフロー](google-play-publication-workflow.md)に従って確認する。結果と残る制約を同じノートへ追記する。Play Consoleの公開状態・公開日時・配布範囲を確認してから公開済みと記録する。
8. ノートを成果物と合わせてバックアップし、保管先と実施日をノートに残す。公開結果だけを理由に仕様書へ履歴を追記したり、計画書を追加コミットしたりしない。動作・契約・手順に誤りが見つかった場合は該当文書を修正し、継続対応はIssuesで管理する。

GitHubでも配布する場合は、そのReleaseの本文・タグ・添付成果物を別途照合する。公開済みタグは動かさない。配布済みコードや成果物の修正は、別のversionCodeで準備する。

### 内部リリースノートの保管

版ごとに`app/release/Nagisa-<versionName>-vc<versionCode>-release-notes.md`を作成し、同じノートへ準備から公開後の結果まで追記する。
この名前のノートは`.gitignore`で除外する。Git管理外のため、成果物と一緒に非公開の保管先へバックアップする。旧版の記録を計画書から移した場合も、移し漏れと参照先を確認して同じ保管先へバックアップする。過去版のノートは当時の記録として保持し、計画書へ更新履歴や検証結果を戻さない。

AABとノートをひとつにまとめる場合は、`app/release/Nagisa-<versionName>-vc<versionCode>-release-package-<日時>.zip`へAAB・同名のSHA-256ファイル・内部ノートを収録する。ZIPもGit管理外とし、外部バックアップは別途行う。

記録する内容は次の範囲とし、未確認・未実施はそのまま明記する。

- versionName・versionCode、比較元、対応するソースのコミットSHA、今回の変更内容。
- 成果物のファイル名・SHA-256、版番号と署名の確認結果。
- 検証した版・構成・日時・端末／OS・サーバー、結果、既知の制約と残るIssue。既存の調査記録はリンクで参照する。
- Playの提出・配布トラック・公開状況と確認日時、公開後の動作確認、バックアップの保管先と実施日。

署名鍵、パスワード、トークン、他人の投稿などはノートへ記録しない。公開状態はPlay Consoleで確認し、ノートにはその確認結果を残す。
