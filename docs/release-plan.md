### v2.4.1に含める更新

- 通知を「すべて」「メンション」「リアクション」別に最大40件ずつ取得し、一覧・カーソルを独立させる。非対応リアクションの連続読込と、取得前の空表示を修正する。
- 通知の既読取得と一覧表示を分離し、再起動・時間経過後の新着件数の過大判定を抑える。Room v3へ移行し、旧通知・既読位置・ホームを保持する。
- 通知欄にも本文・CWのワードミュートを適用し、ワードに一致する返信通知とその新着件数・強調表示を隠す。元の通知とキャッシュは保持する。
- 検索の詳細画面から戻った際にキーボードが再表示される不具合を修正し、検索語・結果・対象・閲覧位置を維持する。
- PushのRelay登録v2に対応し、購読ごとのVAPID公開鍵・仮登録・revisionによる更新を導入する。既存の登録・配送先・暗号鍵を保持して移行する。
- Workers Relayの容量制限・部分停止・FCMエラー分類・再送と復旧手順を整備する。Relayの更新はアプリ配布とは別に実施・検証する。

## 2.4.1の通知修正（2026-10-06）

種類別の一覧とカーソル、最大40件の取得、種類指定が使えない場合の全通知からの絞り込みを実装した。
表示対象が増えない連続2ページで自動遡及を止める。リアクションは`fedibird_capabilities`の`emoji_reaction`が確認できる場合だけ取得する。
同じタブの再表示では対応情報を再利用し、手動更新・前景復帰・新しいセッションで再確認する。

既読取得は5秒の期限と保存値へのフォールバックを設け、待機中の閲覧も保持する。
境界不明のページ全件を新着扱いせず、Room v3で種類別キャッシュと独立した閲覧記録を追加する。
保存・Streaming・追加取得・対応判定はセッション世代で隔離する。
詳細は[通知仕様](ui-guidelines.md#通知の表示更新既読位置)、[ADR 0007](adr/0007-notification-category-pages-and-read-state.md)、[調査記録](investigations/notification-mention-loading-report.md)を参照する。

### 確認結果

初回の関連73件・全単体326件、対応再確認の二重取得修正後の関連31件が成功。
Pixel_10a（Android 17）で通知画面・通知キャッシュ・ホームキャッシュと旧DB移行・投稿タップ・ライフサイクルの計14項目を確認した。
その後の空表示・非対応表示の調整では関連31件と画面・ライフサイクル4件が成功し、Debugアプリ・テストAPKも生成した。
利用者から実機で仕様どおり通知を取得できるとの報告を受けた。
境界不明時の新着件数はサーバー全体の未読総数を保証しない。最新の全体結果は上記334件を参照する。

## 2.4.1の通知欄ワードミュート（2026-10-06）

Issue #1で報告された返信通知の表示を、通知欄の全タブへ共通の本文・CW判定を適用して修正した。
投稿なし通知は残し、非表示通知を新着件数・強調表示・更新結果から除外する。
内部一覧・DB・カーソルは保持し、ワードを解除すると保持中の通知を再表示する。
Android通知は対象外で、通知を止めたい返信元には利用者が通知抑制付きユーザーミュートを使う。自動ユーザーミュートは導入しない。

実装時はユーザー指定によりコンパイルのみ確認した。その後の全単体334件にはワードミュートの回帰3件が含まれ、全タブと件数、投稿なし通知、別アカウント、Streaming返信の非表示・キャッシュ保持・解除時の再表示が成功した。
適用範囲は[現行仕様](ui-guidelines.md#ミュートブロックの設定からの管理)と[ADR 0008](adr/0008-word-mutes-in-notification-lists.md)を参照する。今回のRelease APKの実機確認報告は上記を参照する。

## Relay登録v2と本番互換更新（2026-10-06）

Android・Workersで購読ごとの公開鍵を登録v2へ紐付け、鍵未取得時は24時間の仮登録とする。
revisionで更新・再試行を保護し、配送・暗号文取得・解除はv1を維持する。
本番Relayは同一URL・既存D1を維持して追加マイグレーションを適用した。旧方式の猶予期間は設けず、更新版Androidの起動時に自動移行する。
移行完了までPushは届かず、その間の通知は欠落し得る。通常は手動のオフ→オンを必要としない。

Workersのテスト34件が成功したバンドルを本番へ配置し、エミュレーターの既存Fedibird登録1件の自動移行と、移行後の通知1件の表示を確認した。
記録時点の旧方式の有効登録5件は更新版の起動待ち。通知表示の確認を配送時間の測定や全登録の移行完了とは扱わない。
詳細は[移行手順](relay-production.md)、[通信契約](relay-protocol.md)、[配置・復旧](../relay/workers/setup.md)、[ADR 0010](adr/0010-relay-subscription-key-binding.md)、[実施記録](investigations/relay-production-measurement-20261006.md#手順6既存公開relayの互換更新2026-10-06)を参照する。

## リリース用pushの手順

### push前：対象版と計画書を同時に更新

1. GitHub ReleasesとGitタグを確認し、比較元の公開版と今回の対象版を確定する。同名タグ・Releaseが既にある場合は先に扱いを決める。
2. `app/build.gradle.kts`のversionName・versionCodeを対象版にし、`docs/release-plan.md`の「現行のリリース対象版」を**この版へ切り替える**。以前の公開版の表や確認記録を現行版として残さない。公開状況欄は今回のタグに対応するGitHub Releaseへの参照とし、公開状態は記載しない。
3. 比較元から今回のコミット候補までの差分を確認し、「今回の変更内容」「確認状況」「次回以降の候補」を更新する。今回含まれない変更を引き継がない。
4. `docs/project-setup.md`と`docs/ui-guidelines.md`などの版番号表記を確認する。旧版番号や古い確認記録を文書内検索し、対象版と矛盾がないか確認する。対象版・変更内容・確認結果はこの文書、公開状態・公開日・Pre-release区分はGitHub Releaseを正本とする。
5. 必要なテスト・Releaseビルド・端末確認を行い、実施済みの結果と未確認事項を記録する。署名済みAPKの署名、APK内の版番号、SHA-256も確認する。未実施項目を確認済みと書かない。
6. リリースノートを今回の差分と検証結果から作り、既知の制約を明記する。
7. **コミット直前の必須確認**：コードの版番号、APKの版番号、計画書の現行対象版・変更内容・確認状況、関連文書の版番号が一致することを確認する。`git diff --check`と`git status`でコミット対象を確認し、IDE設定、署名鍵、パスワード、認証情報、生成APKを除外する。
8. コードと**更新済み計画書を同じリリース準備コミット**に含め、注釈付きタグを作成する。ブランチ、タグの順にpushする。計画書が旧版のままならpushしない。

### 公開・公開後：配布内容の一致を確認

9. GitHub ReleaseのPre-release設定、本文、添付APKを確認して公開する。公開しただけではリリース作業を完了としない。
10. 公開ページでPre-release設定、版番号、タグの対象コミット、添付APKのSHA-256を確認し、リリース用push前に確定した計画書・配布候補と一致すればリリース作業を完了とする。公開状態や公開日を計画書へ転記するための追加コミット・pushは行わない。
11. 誤記や不一致があった場合のみ、該当する文書やGitHub Releaseを修正して再確認する。文書を修正した場合は別コミットでブランチへpushする。**公開済みタグは動かさない**。コードやAPKの修正が必要なら、別バージョンのリリースとして扱う。

公開前に作業を止めた場合も、計画書に公開済みとは記さない。Releaseリンクの記載だけでは公開を意味せず、公開状況はGitHub Releaseで確認する。
