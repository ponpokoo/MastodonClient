## 次回リリース候補

比較元は`v0.1.1`。次回版は`2.0.0`（versionCode `6`）で、GitHub ReleaseはPre-release。
公開日は未確定。配布候補は`app/release/app-release.apk`。

### 今回の変更内容

- バックグラウンドのリアルタイム通知：MastodonのWeb Push購読、暗号文の受信・復号、
  Firebase Cloud Messaging、Workers＋D1のRelay、Android通知表示を接続した。
  アカウントごとの有効化、`push`権限の再認証、解除・再試行、トークン更新を扱う。
  実際の通知到着と継続受信は利用者が確認済み。詳細は
  [受信・復号・表示](push-reception.md)、[通知設定](push-settings.md)、
  [Firebase Android接続](firebase-android.md)、[Relay登録API契約](relay-protocol.md)、
  [公開Relayの設定](relay-workers-setup.md)を参照する。
- Fedibirdの絵文字リアクション通知：インスタンスの`fedibird_capabilities`に
  `emoji_reaction`がある場合に限り、Push購読の通知種類へ追加する。
  v2インスタンス情報を優先し、404のときだけv1を参照する。既存購読の再照合にも適用し、
  通常のMastodonへ独自項目を送らない。実際の絵文字リアクション通知の到着は利用者が確認済み。
- Streamingの再接続：SSE専用クライアントの読み取りタイムアウトを無期限にし、
  無通信が続いた後も接続を保つ。Fedibirdで報告された新着停止と同じ原因だったかは未確認。
  再接続中の取りこぼしをHTTPで補完する機能は含まない。
- ホームタイムラインの新着表示：先頭ではStreaming新着を自動表示し、
  閲覧途中では位置を保って件数を表示する。件数表示をタップすると先頭へ移動する。
  HTTP更新中に届いたStreaming新着を保持する。
- 通知一覧の更新：手動・自動更新とも、未表示の新着があるときだけ先頭へ移動する。Streamingで先に追加された通知も新着判定に含める。
- 表示調整：Android通知の小アイコンをNagisaの象の単色シルエットに変更し、引っ張って更新のインジケーター移動距離を調整する。

## 次回以降の候補

以下は今回の配布対象外。採用時に仕様と優先順位を決める。

- 通知欄の通知ごとの既読表現と、OS通知から対象詳細への直接遷移。
- Push有効時の簡易通知スケジュールと、リアルタイム通知・起動中の通知・簡易通知の役割の整理。Streamingをオフにしても前景Pushを受信し得る点を設定説明に反映する。
- お気に入りしたアカウント一覧のダイアログの高さ、固定タイトル、非同期画像読み込みを見直す。
- 長時間のバックグラウンド復帰や手動更新でタイムラインの閲覧位置を保つ挙動を確認する。
- ベルの新着件数と通知一覧の新着表示を同期し、既読とみなす時点を決める。
- 通知の種類を表すアイコン、投稿下部の件数、タイムラインの新着表示、探索タブの構成を見直す。

## リリース用pushの手順

1. GitHub ReleasesとGitタグを確認し、比較元の公開版を確定する。
2. 比較元から配布候補までの差分で「今回の変更内容」を更新する。過去の計画や今回含まれない変更を引き継がない。
3. versionNameとversionCodeを確定し、関連文書の版番号を揃える。
4. 配布候補で必要なテスト、ビルド、端末確認を行い、実行した結果と未確認事項を記録する。
5. 署名済みAPKの署名、APK内の版番号、SHA-256を確認する。
6. リリースノートを今回の差分と検証結果から作り、既知の制約を明記する。
7. `git diff --check`と`git status`でコミット対象を確認する。IDE設定、署名鍵、パスワード、認証情報、生成APKをコミットしない。
8. コードと更新済み計画書をコミットし、注釈付きタグを作成する。ブランチ、タグの順にpushする。
9. GitHub Releaseの公開区分、本文、添付APKを確認して公開する。

同名タグがリモートにある場合は、公開済みReleaseへの影響を確認してから版番号またはタグの扱いを決める。
