## v2.2.0の変更と確認記録

比較元は公開版`v2.1.2`。比較元から今回のリリース準備コミットまでの変更を対象とする。
2.1.2に含まれる引用方式・返信解除・リアクション表示設定などは、新規変更として再掲しない。

### 今回の変更内容

#### ホームの端末保存

- ホームタイムラインをアカウント・インスタンス別にDBへ最大500行保存する。初回・追加取得は20件で、保存済みページを先に表示してから同じページを通信で更新する。残り5件を目安に続きを先読みする。
- 閲覧位置の復元に保存済み範囲を利用する。オフラインや自動更新の失敗時は保存済み一覧を維持し、手動更新・保存なしの取得失敗は再試行できるエラーを表示する。
- サーバーが要求件数より少ない投稿を返しても履歴の末尾と決めつけず、空のページまで追加取得できるようにする。
- 未取得区間を飛ばさず、ブーストをタイムライン行として区別する。通信中の投稿操作・Streamingによる変更を反映し、投票結果も保存する。アカウント切替・ログアウト時は保存と遅延処理を分離する。
- 通知を保持したままRoomスキーマv1からv2へ移行する。ローカル・連合タイムラインは従来の通信取得とメモリ管理を継続する。詳細は[ホームの端末保存](ui-guidelines.md#ホームの端末保存)を参照。

#### サムネイル表示

- 添付メディアとURLカードのサムネイルを、画像の縦横比に合わせた可変サイズに変更し、切り抜かず全体を表示する。縦長画像は高さ上限に合わせて幅も縮小し、寸法情報がない場合は読み込み後に調整する。
- 複数枚の画像は同じ行で高さを揃え、8 dp間隔で左から並べる。合計幅が投稿幅を超える場合は行全体を縮小し、縦長画像同士が小さく離れて見える状態を改善する。
- コンパクト／標準／大の設定で上限を切り替える。現在のコードでは添付1枚の高さ上限は180／280／400 dp、複数枚は220／280／340 dp。
- 複数枚の順序、ビューア・URLへのタップ操作、閲覧注意と自動再生の設定を引き継ぐ。

#### ホーム先頭への移動

- ホームアイコン、新着件数、更新後に先頭へ戻る設定での移動を改善する。長い移動では先頭近くまで移動してからアニメーションし、投稿の高さによって先頭へ戻るまでの時間が長くなることを抑える。
- 先頭の投稿・オフセット0まで移動し、移動中のスワイプや画面・アカウントの切替によるキャンセルを尊重する。

#### リンク閲覧

- 通常のHTTP／HTTPSリンク閲覧を独自WebViewからCustom Tabsへ切り替える。「リンクをアプリ内で開く」の設定を引き継ぎ、既定の対応ブラウザーを優先する。
- ページ内のIntentリンク、共有などはブラウザー側へ任せる。ハッシュタグ表示とYouTube優先の既存動作は維持する。
- Custom Tabsの未対応・起動失敗時はAndroid標準のURL処理へフォールバックし、開けない場合はエラーを表示する。旧WebViewの保存済み画面履歴も引き継ぎ、元の画面へ戻れるようにする。

#### 通知アイコン・文書

- 通知の小アイコンを横向きの象に変更する。単色の塗りつぶしに耳と目の抜きを設け、通知欄で判別しやすくする。余白を詰め、形と縦横比を保って拡大する。
- README、UI・機能仕様、開発ガイドにホーム保存とリンク閲覧の挙動、サムネイル表示、確認手順を反映する。

### 既知の制約

- DB保存は通知とホームが対象。ホームは最大500行、通知は最新200件をアカウント・インスタンス別に保存する。件数は端末保存の上限であり、オンラインで閲覧できる履歴の上限ではない。画像本体・認証情報はDBへ保存しない。
- ホームDB化の継続確認と表示速度・保存容量の評価は継続中。ローカル・連合のDB化と、表示データ全体をDB中心にする移行は次回以降の候補とする。
- Custom Tabsの利用可否とページ内の外部アプリ起動条件はブラウザーに依存する。Cookie・サイトログイン状態はMastodonのアカウント切替とは別に管理される。

### 品質・基盤候補

- ホームDB化は2.2.0のリリース対象に含む。次の拡張は、実機での表示速度、DB本体・書き込み用ファイルの容量、通信失敗時の使い勝手を評価して対象を決める。ローカル・連合のDB化や全画面の唯一のデータ源への移行は未採用。
- 今後も`BrowsingDatabase`のテーブル・DAOとRepository／ローカルデータソースの境界を使い、通知・ホームの保存を保持するマイグレーションを行う。投稿・アカウントの共通テーブル化は必要になる段階で検討する。

採用項目が決まったら、比較元の公開版と版番号を確定し、この節から次回版の変更内容へ移す。

## リリース用pushの手順

### push前：対象版と計画書を同時に更新

1. GitHub ReleasesとGitタグを確認し、比較元の公開版と今回の対象版を確定する。同名タグ・Releaseが既にある場合は先に扱いを決める。
2. `app/build.gradle.kts`のversionName・versionCodeを対象版にし、`docs/release-plan.md`の「現行のリリース対象版」を**この版へ切り替える**。以前の公開版の表や確認記録を現行版として残さない。公開状況欄は今回のタグに対応するGitHub Releaseへの参照とし、公開状態は記載しない。
3. 比較元から今回のコミット候補までの差分を確認し、「今回の変更内容」「確認状況」「次回以降の候補」を更新する。今回含まれない変更を引き継がない。
4. `docs/project-setup.md`と`docs/ui-guidelines.md`などの版番号表記を確認する。旧版番号や古い確認記録を文書内検索し、対象版と矛盾がないか確認する。対象版・変更内容・確認結果はこの文書、公開状態・公開日・Pre-release区分はGitHub Releaseを正本とする。
5. 必要なテスト・Releaseビルド・端末確認を行い、実施済みの結果と未確認事項を記録する。署名済みAPKの署名、APK内の版番号、SHA-256も確認する。未実施項目を確認済みと書かない。
6. リリースノートを今回の差分と検証結果から作り、既知の制約を明記する。
7. **コミット直前の必須確認**：コードの版番号、APKの版番号、計画書の現行対象版・変更内容・確認状況、関連文書の版番号が一致することを確認する。`git diff --check`と`git status`でコミット対象を確認し、IDE設定、署名鍵、パスワード、認証情報、生成APKを除外する。
8. コードと**更新済み計画書を同じリリース準備コミット**に含め、注釈付きタグを作成する。ブランチ、タグの順にpushする。計画書が旧版のままならpushしない。

### 公開・公開後：配布内容の一致を確認

9. GitHub ReleaseのPre-release設定、本文、添付APKを確認して公開する。公開しただけではリリース作業を完了としない。
10. 公開ページでPre-release設定、版番号、タグの対象コミット、添付APKのSHA-256を確認し、リリース用push前に確定した計画書・配布候補と一致すればリリース作業を完了とする。公開状態や公開日を計画書へ転記するための追加コミット・pushは行わない。
11. 誤記や不一致があった場合のみ、該当する文書やGitHub Releaseを修正して再確認する。文書を修正した場合は別コミットでブランチへpushする。**公開済みタグは動かさない**。コードやAPKの修正が必要なら、別バージョンのリリースとして扱う。

公開前に作業を止めた場合も、計画書に公開済みとは記さない。Releaseリンクの記載だけでは公開を意味せず、公開状況はGitHub Releaseで確認する。
