# ADR 0002：通知・ホームに限定した永続キャッシュ

- 状態：accepted（既存設計の追記）
- 記録日：2026-10-05
- 当初の採用日・比較経緯：不明。以下の理由・代替案の評価・見直し条件は現行仕様と実装を基に今回整理した。

## 背景

通知・ホームは再起動後や通信できない場面でも保存済みの一覧を表示する。
保存にはセッション・インスタンスの分離、一覧の順序、通信や操作結果との整合、スキーマ移行が必要。
ローカル・連合は通信取得とメモリ上の状態管理を使用している。

## 決定と理由

通知とホームを`BrowsingDatabase`（Room）の専用テーブルへ保存し、Repositoryとローカルデータソース経由で扱う。
セッション・インスタンス別に件数を制限し、ログアウト時には対象セッションの保存を削除する。
保存済み一覧を先に表示し、通信・Streaming・投稿操作の結果を反映する表示キャッシュとして使用する。
全画面の唯一のデータ源への移行、ローカル・連合のDB化、投稿・アカウントの共通テーブル化は未採用。
通知・ホームの保存を継続しながら、他の一覧へ保存と整合管理の責務を広げる範囲は利用状況を評価して決める。

## 代替案の評価（今回の整理）

- メモリのみ：永続保存の責務は減るが、再起動後やオフライン時に保存済み一覧を利用できない。
- 全一覧をDB化：保存済み閲覧の範囲は広がるが、保存量・更新処理・履歴の接続を扱う範囲も増える。
- DBを全画面の唯一のデータ源にする：共有データの整合を集約できるが、読み取り・更新経路とデータ構造の移行が必要になる。

## 受け入れる制約

ローカル・連合の永続保存は提供せず、保存上限を超えた履歴はキャッシュから閲覧できない。
画面・Repositoryの状態とDBの整合管理は引き続き必要。未取得区間を保存済み履歴で飛ばさない。
スキーマ変更では既存の通知・ホームの保存を保持するマイグレーションを行う。

## 見直し条件

表示速度、DB・書き込み用ファイルの容量、通信失敗時の使い勝手を評価して保存対象の拡張を検討する。
画面間の整合管理が重複・複雑化した場合は、共通テーブル化や全画面のデータ源への移行を再検討する。
