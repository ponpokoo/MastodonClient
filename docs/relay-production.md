# Relay本運用への移行手順書

- 作成日：2026-10-06
- 状態：計画。配置先・公開URL・本運用開始日は未定。
- 対象：任意の対応MastodonサーバーからWeb Pushを受け、FCMでNagisaへ中継するRelay。

本書は配置先に依存しない準備・実装・検証・移行・運用の手順を定める。
ここに記載する本運用向け変更は未実装であり、現行版の機能や公開完了を示さない。
配置先を決める前でも手順1〜3の設計・実装を進められる。公開は手順4〜6を満たしてから行う。
Mastodon互換サーバーもPush API・署名・暗号形式の対応を確認し、すべてのサーバーで配送できるとは扱わない。

## 参照と現在の状態

現行の通信形式は[Relay共通契約](relay-protocol.md)、購読の状態管理は[通知設定](push-settings.md)、
Firebase・端末受信は[Android接続と受信処理](push-reception.md)を参照する。
情報の境界は[ADR 0003](adr/0003-push-relay-responsibilities.md)を維持する。

| 項目 | 現行実装 | 本運用前に行うこと |
| --- | --- | --- |
| Workers版 | 実FCM送信、D1保存、VAPID検証あり | 配置先として継続するか選定し、下記の不足を解消する |
| Node.jsローカル版 | 模擬FCM送信、VAPID検証なし、単一プロセス用ファイル保存 | 公開用サーバーとしてそのまま使用しない。別環境への移植時は本番用の配送・保存・認証を実装する |
| 許可するサーバー鍵 | Workers全体に手動設定、最大20鍵 | 購読ごとの自動登録・照合へ変更する |
| 鍵の紐付け | 許可リスト内のどの鍵でも配送URLへ送信可能 | 各配送先で、その購読に紐付く鍵だけを許可する |
| 登録API | v1本文は`fcmToken`のみ。追加フィールドを拒否 | 鍵登録・更新と旧クライアント互換性を定義する |
| Workersの件数上限 | 墓標込み登録100件、保持通知200件、登録別20件、UTC日次2000要求 | 規模・負荷試験・費用に基づく上限へ変更する |
| Workersの再送 | 初回は受付後に送信、Cronは毎回最大1件 | 障害後の滞留を期限内に処理できる構成にする |
| 削除済み登録 | 墓標を無期限保持 | 遅延登録による復活防止と保管費用を両立する方針を決める |
| 配送完了の意味 | FCM受付成功。端末表示の確認ではない | 受付・FCM送信・端末表示を分けて検証・監視する |

現行の詳細・過去の検証は[Workers版README](../relay/workers/README.md)、
[Workers試験環境の配置手順](../relay/workers/setup.md)、[ローカル版README](../relay/README.md)を参照する。
過去の配信成功は、新しい構成での負荷・復旧・実機検証の代わりにはならない。

## 手順1：本運用の条件を決める

1. 運用責任者、障害時の連絡先、公開対象、初期利用人数を決める。
2. 下表の未定項目を埋め、負荷試験と公開判断の基準にする。
3. 公開範囲を段階的に広げる単位と、拡大を停止する条件を決める。
4. 配置先と契約の設計を採用する時点で必要なADRを追加し、本書・現行仕様と相互リンクする。
   本書の案だけで既存の通信契約やacceptedの設計判断を変更しない。

| 決めること | 記録する値・条件 | 現在 |
| --- | --- | --- |
| 利用規模 | 利用人数、1人あたりのアカウント・端末数、総購読数 | 未定 |
| 流量 | 通常・ピークのPush要求/秒、日次件数、本文サイズ分布 | 未定 |
| 配送目標 | Relay受付からFCM受付までの時間と成功率、計測期間 | 未定 |
| 復旧目標 | RTO（復旧時間）、RPO（許容する保存データの損失期間） | 未定 |
| 障害時の容量 | 想定FCM停止時間、最大滞留件数、復旧後に解消する時間 | 未定 |
| 費用 | 月次予算、警戒額、上限接近時の対応 | 未定 |
| 保持期間 | 暗号文、無効登録、墓標、バックアップ、集計情報の保持期間 | 未定 |
| 段階公開 | 各段階の購読上限・観測期間・停止閾値 | 未定 |

現在のTTL上限は24時間であり、停止中も期限は延長しない。復旧目標は通知の有効期限を考慮する。
FCM受付の目標と端末表示の観測は別に記録する。端末のオフライン・OS制限を含む即時表示は保証しない。

## 手順2：配置先を選定する

1. HTTPS受付、永続DB、背景での送信・再送、秘密情報管理、監視、バックアップを満たす候補を挙げる。
2. 下表と手順1の値で比較し、試作・負荷試験の結果から選ぶ。無料枠を前提に決定しない。
3. 最終決定時に、料金・実行制限・保存地域・復元機能を各サービスの最新の公式資料で確認する。
4. 環境固有の配置コマンド・変数・DB初期化・復元・停止手順を別の配置手順にまとめ、本書と一覧へリンクする。

| 候補の種類 | 検討する構成 | 比較する点 |
| --- | --- | --- |
| Workers等のサーバーレス | HTTPS受付、永続DB、キューまたは定期再送 | 実行時間・CPU・DB・キュー制限、再送処理量、保存地域、費用。既存Workersコードの継続利用を評価する |
| 管理されたコンテナ環境 | 受付サービス、送信Worker、管理DB・キュー | 最小稼働数、背景処理の保証、スケール、認証、復元。Workers固有APIからの移植量を評価する |
| VPS等の常駐環境 | リバースプロキシ、受付・送信プロセス、DB | TLS更新、OS更新、監視、バックアップ、障害対応の担当と費用。本番用実装を別途用意する |

可能ならアプリに埋め込む公開originは長期維持できるものにする。独自ドメインの採用もここで決める。
配置先だけを変え、origin・パス・保存情報を維持する移行と、公開URLを変える移行では手順が異なる。
URLが同じでもDBを空にすると既存の配送先は失われる。

## 手順3：配置先に依存しない実装変更を行う

### 3.1 購読単位のVAPID鍵登録

推奨案は、Androidが選択アカウントのサーバーから公開鍵を取得し、Relayの登録に紐付ける方式。
Relayが利用者指定のURLへ鍵を取得しに行く方式は採用案に含めない。
これによりRelayにMastodonの認証情報を渡さず、鍵取得のための任意URLアクセスも不要にできる。

1. AndroidのdomainモデルにサーバーのVAPID公開鍵を保持できるようにする。DTOをUIへ渡さない。
2. `/api/v2/instance`の`configuration.vapid.public_key`を確認する。項目がない、またはAPIが404の場合は
   Push購読API応答の`server_key`を利用する経路を用意する。401／403や通信失敗をAPI非対応と誤認しない。
3. 新しいRelay登録契約に公開鍵の登録・確定・変更の操作を定義する。既存v1へフィールドを足すだけでは
   現行Relayが拒否するため、バージョンまたは機能判定と展開順序を明示する。
4. 公開鍵を先に取得できないサーバーでは、配送先の仮登録 → Mastodon購読登録 → `server_key`で鍵確定とする。
   仮登録中はPushを配送せず、アプリも「有効」にしない。途中停止・応答消失から再開できるよう進捗を保存する。
   確定前に発生した通知は欠落し得るため、この制約を設定仕様に記録する。
5. RelayはP-256公開鍵の形式を検証・正規化して登録に保存する。管理用トークンの認証なしに変更を許可しない。
6. Push受付では配送先の登録状態・登録鍵との一致・署名・audience・有効期限を検証してから保存・配送する。
   標準VAPIDと現行の旧WebPush認証の互換性を維持する。
7. 公開鍵の取得・確定・購読登録が完了して初めてアプリの状態を「有効」にする。
   「有効」が実際の通知表示まで確認した状態ではないことは維持する。

このRelay独自APIの案は、RFCのWeb Push購読作成APIをそのまま実装したものではない。
購読を特定の公開鍵に制限する考え方は[RFC 8292 §4](https://www.rfc-editor.org/rfc/rfc8292.html#section-4)、
鍵の取得元は[Mastodon Instance](https://docs.joinmastodon.org/entities/Instance/)と
[WebPushSubscription](https://docs.joinmastodon.org/entities/WebPushSubscription/)を参照する。

公開鍵がどちらのAPIからも得られない場合は対応未確認として再試行・説明を表示する。
最初に届いたPushの鍵を自動的に信頼したり、全体の許可リストへ無条件追加したりしない。

### 3.2 鍵変更・トークン変更・解除

- 鍵変更はAndroidが対象サーバーのHTTPS APIを再確認して管理用認証で更新する。取得できない状態で鍵を差し替えない。
  旧鍵を併用するか、再購読するか、未起動端末へどう案内するかを契約で決める。
- FCMトークン更新では配送endpoint・登録鍵を維持する。鍵の変更操作とトークン更新を混同しない。
- 登録・鍵確定・更新は同じ要求を再送しても整合するようにし、同時更新・古い応答で状態を巻き戻さない。
- アカウントごとに登録を分離し、再認証・ログアウト中の処理と通知表示を隔離する。
  [セッションとキャンセル方針](project-setup.md#メイン画面の責務とライフサイクル)に従う。
- 解除はRelay配送停止 → 対象Mastodon購読の照合・解除 → ローカル削除を維持する。
  解除待ちを保存してから認証情報を破棄し、旧Relayへの再試行を維持する。

### 3.3 登録の濫用防止と容量

1. 新規登録、既存登録更新、Push受付、暗号文取得、解除を分けて制限する。
   全体の登録・通知上限を使い切ったことで正当な解除や既存端末の更新ができない状態を避ける。
2. 登録元・購読ごとの頻度、本文サイズ、同時処理数、全体容量、入口での拒否を設計する。
   仮登録には期限・件数制限を設け、未完了データが容量を占有し続けないようにする。
3. 初回登録の管理用トークンはクライアント自身が作るため、それだけでは正規アプリの利用証明にならない。
   公開範囲に応じて配布・登録資格の確認方法を決め、APK内の共通秘密値だけに依存しない。
4. 429の再試行間隔と費用上限接近時の対応を定義する。拒否した要求にも課金や検証コストが生じる前提で測定する。
5. 墓標を削除するなら、古い登録IDの再利用・遅延PUTを拒否できる世代または期限の仕組みを先に実装する。
   現行のランダムIDだけでは安全な受付期限を判断できないため、保持日数だけで墓標を消さない。

### 3.4 配送と再送

1. 保存を完了してから201を返す。処理中断後も未送信の通知を復旧できるようにする。
2. 期限内の初回送信・再送を永続キューまたはDBから実行し、複数Workerの排他・リース期限を設計する。
   障害復旧時も登録間の公平性と送信量制限を維持する。
3. 指数バックオフ、ジッター、`Retry-After`、送信タイムアウト、試行回数・TTL上限を定義する。
   現行Workersの7秒タイムアウトも含め、FCMの最新推奨と選定環境の実行制限に照らして見直す。
4. `UNREGISTERED`などの型付きエラーと一般的なHTTPエラーを区別する。
   無効トークンは停止し、認証・プロジェクト不一致・不正本文は修正が必要なエラーとして通知する。
   一律に再送したり、一般的な400／404で端末を無効化したりしない。
5. 旧FCMトークンへの送信結果で新しいトークンを無効化しない。解除後の再送・取得も拒否する。
6. FCMはdataメッセージを維持し、本文サイズに応じてinline／fetchを使う。
   重複配送はあり得るため端末側の通知IDによる重複排除を維持する。TTL 0・期限切れは配送しない。

再送・エラー分類の根拠は[FCMの負荷と再試行](https://firebase.google.com/docs/cloud-messaging/scale-fcm)、
[FCMエラーコード](https://firebase.google.com/docs/cloud-messaging/error-codes)を参照する。

### 3.5 情報管理と仕様更新

- RelayへMastodonアクセストークン、OAuth client secret、Web Push秘密鍵・auth secretを送らない。
  公開鍵は登録できるが、通知の復号は引き続きAndroidで行う。
- 管理用トークンは検証用ハッシュで保持し、FCMトークン・配送ID・暗号文の閲覧権限を限定する。
- ログ・APM・プロキシ・アクセスログを含め、Authorization、FCMトークン、管理用トークン、
  サービスアカウント秘密鍵、配送endpoint URL、復号済み本文を記録しない。
- 暗号文は期限まで、解除時は関連データを削除する。無効登録・墓標・バックアップの保持・削除は手順1の方針に従う。
  バックアップからの復元で解除済み登録を復活させない手順も設計する。
- 変更を実装した段階で[共通契約](relay-protocol.md)、[購読管理](push-settings.md)、
  [Android受信](push-reception.md)、各RelayのREADME、必要なADRを更新する。
  ローカル版と本番版が提供する機能の差を明記する。

## 手順4：選定した環境へ検証用Relayを配置する

1. 試験環境と本番環境のDB・キュー・秘密情報・運用権限を分離する。
2. HTTPS・公開origin・必要な受付パスを設定し、証明書更新と時刻同期を確認する。
   VAPIDのaudienceと期限検証に関わる。登録で返すendpointと実際の公開originを一致させる。
3. DBのマイグレーションとキュー・再送実行を構成し、停止・再起動・並列実行でも保存情報を維持する。
4. AndroidのFirebase設定と一致するプロジェクトを送信先にする。FCM APIと必要な送信権限を確認する。
   実行環境が対応するなら短期認証・管理された認証を評価し、秘密鍵が必要ならSecretsに置き、更新手順を作る。
5. 集計監視・通知先・費用監視を設定し、自動ログへ秘密値や配送URLが入らないことを確認する。
6. DB・保存情報のバックアップと隔離環境への復元を実行し、手順1のRTO・RPOを満たすか記録する。
   復元試験では実端末へ送信しない。復元後に解除済み登録を再開しないことを確認する。
7. 構成ファイル、DBマイグレーション、配置対象コミット・成果物、戻せる版を記録する。
   記録に秘密値や配送endpointを含めない。

Workersを選ぶ場合は[既存の配置手順](../relay/workers/setup.md)を出発点にするが、
全体の鍵リスト・試験件数上限・毎分1件の再送をそのまま本運用条件としない。

## 手順5：公開前の検証を行う

### 自動検証

変更したRelay実装のディレクトリで`npm test`を実行する。
Workers版はそのREADMEのランタイムと依存関係導入手順に従う。両実装を変更したら両方で実行する。
Androidの変更は[開発ガイドの確認範囲](project-setup.md#ビルドと確認)に従い、影響するテストから始める。

| 観点 | 必須の確認 |
| --- | --- |
| 鍵登録 | 事前取得・購読応答からの取得、仮登録、確定前の拒否、応答消失と再開、キー不正 |
| 送信元の隔離 | Aの鍵でAの配送先へ送信成功、Aの鍵でBの配送先は拒否、未登録鍵・無署名・改ざん・期限・audience不一致は拒否 |
| 認証・更新 | 別管理トークンの更新・解除・取得を拒否、冪等な登録、鍵・FCMトークン更新の競合 |
| 解除 | 解除後のPushと取得を拒否、遅延PUTで復活しない、ログアウト・再認証中の配送抑止 |
| 互換性 | 新旧クライアントと新旧Relayの組合せ、旧署名・暗号形式、未対応API・未知フィールド |
| 配送障害 | 保存後の中断、FCM停止、リース切れ、再送競合、429・認証不良・無効トークン、TTL失効 |
| 容量と復元 | 大きなfetch通知、上限時の拒否と解除・更新、DB移行、バックアップ復元と墓標維持 |

### 実配信・負荷・運用検証

1. 検証用アカウントを異なるサーバーで登録し、手動の公開鍵追加なしでPushを有効化する。
   事前に鍵が取得できる経路と、購読応答から取得する経路を確認する。使えない経路は未検証と記録する。
2. 新しいメンション等を発生させ、Mastodon → Relay受付 → FCM受付 → Android受信・復号・表示を確認する。
   Firebase Consoleのnotificationメッセージや`/health`の成功だけで完了としない。
3. 前景・背景・画面消灯・Doze・ネットワーク切断・再起動・アカウント切替を実機で確認する。
   強制停止時のOS制約と、次回起動後の再開を区別して記録する。
4. 手順1の流量で負荷試験し、FCM停止を模擬して滞留・復旧・期限切れを測る。
   大量送信は模擬FCMを使い、実FCMは管理した少量の確認で扱う。
5. 実行時間、DB・キュー使用量、失敗率、滞留、費用の見積もりを記録する。
   無料枠の過去実績やローカル実行時間で本番環境の制限内と判断しない。
6. 停止・復旧・秘密情報更新を担当者が手順どおり実施し、監視通知が届くことを確認する。

検証記録には版・環境・条件・日時・結果・残る制約を残す。秘密値や配送URLを証跡へ貼らない。

## 手順6：既存の試験購読から段階的に切り替える

### 6.1 URLを維持する場合

1. DBへ鍵・状態等の列を追加する互換マイグレーションを先行し、旧登録・配送ID・墓標・キューを保持する。
2. 新契約に対応したRelayを先に配置する。旧登録にサーバー鍵がない状態の扱いを事前に決める。
   旧方式の限定継続には期限を設けるか、更新完了まで配送を停止して案内する。
   最初に届く署名から鍵を推測して登録しない。
3. Androidを更新し、既存購読の鍵をAPIから取得して紐付ける。暗号鍵とendpointを不要に再生成しない。
4. 更新状況と送信元拒否率を監視し、旧クライアントへの通知と移行期限を運用記録に残す。
5. 移行完了を確認して旧登録方式と全体鍵リストへの依存を終了する。

### 6.2 URLを変更する場合

現在のAndroidは保存済みRelayを既存購読の更新・解除に使うため、ビルドのRelay URLを変更するだけでは移行しない。
新Relayへの明示的な移行処理または利用者によるオフ→解除完了→オンの操作と案内を用意する。

1. 旧Relayを維持したまま、新Relayと対応Androidを少数端末で検証する。
2. 旧Relayへの配送停止・旧Mastodon購読解除を完了し、新しい登録ID・配送先で新Relayへ登録する。
   解除中やオフラインで中断した場合は状態を保存し、再開する。購読APIが既存購読を置換することに注意する。
3. アカウントごとの移行完了と新経路の実配信を確認する。解除から新登録までの通知欠落は起こり得る。
4. 旧版利用者・長期未起動端末の扱い、旧URLを維持する期限、解除待ちへの対応を決めて案内する。
5. 移行対象の完了・残存登録・期限を確認して旧Relayを停止する。稼働中の旧DBを空にして切り替えない。

公開範囲の各段階で手順1の観測期間・閾値を満たしたら次へ進む。
送信元検証の欠陥、保存データの不整合、閾値を超える失敗・滞留・費用があれば拡大を停止する。

## 手順7：日常監視・障害対応・復旧

### 日常監視

- 集計する：受付成功率と応答コード、鍵拒否、登録・解除失敗、FCM受付成功率、失敗の分類、
  キュー件数・最古の未送信経過時間・期限切れ件数、再送稼働、DB・実行量・費用。
- 警戒・停止の閾値と確認間隔は手順1の値から設定する。
  FCM受付済みを端末表示済みと表示しない。端末表示は検証端末で別途観測する。
- 実行環境、依存関係、TLS、FCMの認証情報・権限を定期確認する。
  秘密情報の更新・失効・漏えい時の対応と担当を配置先の手順に残す。
- 定期的に隔離環境で復元試験し、保存・削除方針と監視の有効性を確認する。

### 届かない場合の切り分け

| 観測 | 確認する箇所・対応 |
| --- | --- |
| 特定サーバーだけ拒否 | サーバーの現行公開鍵、購読の登録鍵、署名・期限・audience、サーバーからRelayへの接続を確認する |
| Relayへ要求がない | アプリの購読状態・配送先、対象通知種類、Mastodon側の通知発生・送信処理を確認する |
| 受付後にFCMへ送れていない | DB・再送実行・滞留・FCM認証とプロジェクト・型付きエラーを確認する |
| FCM受付済みで表示されない | 端末の通知許可、前景設定、WorkManager、期限、購読照合、復号、重複排除、OS状態を確認する |
| 全体の429・滞留増加 | 入口の制限、DB・キュー容量、再送処理量、費用を確認する。検証なしに上限だけ引き上げない |

### 停止・ロールバック・データ復旧

1. 新規登録停止、Push受付停止、送信停止を区別して実行できる手順を用意する。
   計画停止なら解除・取得に必要な経路を可能な限り維持する。現行Workersの`RELAY_ENABLED=false`は
   登録・解除・取得も停止するため、本番の部分停止機能とは扱わない。
2. FCMがすでに受け付けた通知は取り消せない。送信停止と端末側の購読照合の限界を記録する。
3. コードの差し戻しは新スキーマ・新登録契約と互換な版へ行う。新しい鍵制限を無視する旧版へ戻さない。
   データを失うDBの巻き戻しを通常のロールバックにせず、必要なら修正版を前進適用する。
4. DB復元が必要なら受付・送信を止め、バックアップ後の解除を反映してから再開する。
   解除情報を再構成できない場合は復元した購読を配送停止のままにし、端末で再登録する方針を取る。
5. URL変更後に戻す場合は購読の再移行が必要。Androidの接続先設定だけを戻して復旧完了としない。
6. 復旧後は少数の検証購読で隔離・解除・実配送を確認し、徐々に再開する。発生・復旧時間、影響、欠落、対策を記録する。
