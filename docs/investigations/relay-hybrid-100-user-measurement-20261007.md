## 判断

**ハイブリッドを第一候補として維持する。本文保存・取得と永続再送を除くことで、旧方式のD1ボトルネックは大幅に軽減した。**
通常分布1,000件では読取約92%、書込約70%減。大通知だけでも本文保持0で処理費用は購読数・通知数にほぼ比例し、
旧方式の本文件数に応じたCOUNT走査の増加を避けられる。
Androidの差分同期が未実装で、通常の内部エラー1件とCPU上位値も未解決。候補の資源削減と公開可否を別に判断する。

## 負荷測定

通常は1,000件を600ms間隔、集中は500件を120ms間隔。
分布は1KiB 90%／4KiB 9%／64KiB 1%。全1KiB・全4KiBは各1,000件を120ms間隔で別に測った。
最大同時実行16、TTL24時間。実際の流入14.4秒間隔を24時間再現する試験ではない。
HTTPの失敗、集計未完了を成功へ含めない。FCM受付時間は端末表示時間とは区別する。

| 条件 | 要求／201受付 | inline／同期トリガー | D1読取／書込 | 本文保持 |
| --- | --- | --- | --- | --- |
| 通常分布 | 1,000／999（500が1件） | 899／100 | 5,001／2,992行 | 0 |
| 集中分布 | 500／500 | 450／50 | 2,689／1,311行 | 0 |
| 全小通知1KiB・再測定 | 1,000／1,000 | 1,000／0 | 5,427／2,573行 | 0 |
| 全大通知4KiB | 1,000／1,000 | 0／1,000 | 5,497／2,503行 | 0 |

FCM受付はそれぞれ999／500／1,000／1,000件で、成功要求はすべて60秒内に模擬FCMが受け付けた。
HTTP応答のp50／p95／p99／最大は通常184／219／271／621ms、集中194／243／314／350ms、
全小通知242／328／428／547ms、全大通知246／323／384／452ms。
上表の各フェーズで新たな集計未完了0件、通信例外0件。通常はSQL3,998文、集中は2,000文、全小・全大は各4,000文。
更新後の全小・全大は測定記録の保存待ちを含むため、更新前の通常・集中と応答速度の優劣を判定しない。

全小通知の初回はHTTP 201が1,000件だったが、完了した記録は999件、未完了1件。
初回のD1読取5,434／書込2,558行は部分集計として保存し、上表には再測定を使う。
初回記録は消していないため、DB全体の累積未完了は1件のまま。再測定はフェーズ前後の差分で確認した。

通常の内部エラー1件はFCM送信前、実行したSQL2文の段階で発生した。
destination取得後の頻度処理まで進んだことが集計から分かるが、例外の原因は未特定。
アプリのHTTP 500を捕捉して応答しているため、Workers Metricsの例外0件とは別に数える。
500の原因を確定する前に成功率100%の条件達成とは扱わない。

## 日次費用で加える項目

Pushの平均だけで判定せず、低頻度では毎回新しい頻度カウンター行になる点を補う。
通常の各購読は約48分に1通知のため、新しい頻度行のINSERT（索引込み2書込）と日次更新1書込で3行/通知を採る。
今回の清掃実測から期限切れカウンター削除は1書込/行を採る。

| 項目 | 6,000通知/日の見積もり |
| --- | --- |
| Push受付 | 読取6行×6,000＝36,000、書込3行×6,000＝18,000 |
| 日次清掃 | 読取約6,000頻度行＋200登録＋数行、書込約6,000＋古い日次行 |
| 合計 | 読取約42,200行/日、書込約24,000行/日 |

Freeの読取5M／書込100k行/日に対し、それぞれ約0.85%／24%。これらは日次実測ではなく外挿値。
索引・スキーマが変われば再測定する。登録更新・解除・無効化、拒否要求、他DBの利用、
監視・測定の追加SQLはこの通常運用分と別に加える。短時間の全大通知平均2.503書込/通知だけを日次費用へ使わない。
本文保存・取得・配送retry用のSQLはなくなるが、受付の頻度・日次カウンターは残る。
Androidの追加APIは実装後に測る。同期比率10%なら6,000×0.1＝600トリガー/日で、
集約・ページング・失敗・起動時補完により実リクエスト数は変わる。

## 次に進める条件

1. HTTP 500のSQL段階を匿名エラー分類で切り分け、通常条件を再測定する。
2. 測定ラッパーを減らし、実FCMを含むCPUの上位値と受付時間を確認する。

本測定はRelay候補の評価まで。Android実装と本番切替は次工程。
